Part III · Chapter 16

The filing cabinet.

The topo service stores everything Vitess processes need to coordinate: which shards exist, which tablet is primary, what the sharding key is. Everyone reads it; only the control plane writes it.

Learning objectives

By the end of this chapter, you will
  • List the things stored in topo (keyspaces, shards, tablets, vschema, locks).
  • Explain the global vs. cell-local split.
  • Use vtctldclient to read topo state from your local cluster.
  • Find the Conn interface in go/vt/topo/conn.go and recognize it as a versioned KV store.

What lives in the topo

  • Cells — list of cells & how to reach their topo
  • Keyspaces — logical databases; their sharding config
  • Shards — slices of a keyspace by key range
  • Tablets — each vttablet's record (host, port, type, etc.)
  • VSchema — sharding rules (vindexes, tables → vindexes)
  • SrvKeyspace — per-cell serving view of a keyspace (what vtgate uses)
  • Routing rules — workflow-time hints for MoveTables
  • Locks — coordinate destructive operations

Global vs cell-local

flowchart LR Global[(global topo
keyspaces, vschema, locks)] Cell1[(cell us-east
tablets, SrvKeyspace)] Cell2[(cell us-west
tablets, SrvKeyspace)] Global -.references.-> Cell1 Global -.references.-> Cell2
  • The global topo holds the cluster-wide schema (keyspaces, vschema, locks).
  • Each cell has its own topo holding the tablets/serving data for that DC.
  • vtgate reads its cell's topo for serving; vtctld coordinates via global.

The pluggable interface

// in go/vt/topo/conn.go (abridged)
type Conn interface {
    Create(ctx context.Context, filePath string, contents []byte) (Version, error)
    Update(ctx context.Context, filePath string, contents []byte, version Version) (Version, error)
    Get(ctx context.Context, filePath string) ([]byte, Version, error)
    Delete(ctx context.Context, filePath string, version Version) error
    List(ctx context.Context, filePathPrefix string) ([]KVInfo, error)
    Watch(ctx context.Context, filePath string) (current *WatchData, changes <-chan *WatchData, err error)
    NewLeaderParticipation(name, id string) (LeaderParticipation, error)
    Lock(ctx context.Context, dirPath, contents string) (LockDescriptor, error)
    Close()
}
go/vt/topo/conn.go

It's a versioned key-value store with watch + lock. Anything with those primitives can back Vitess.

Reading topo: GetShard

Conceptually:

  1. Compute the file path: /keyspaces/<keyspace>/shards/<shard>/Shard
  2. Call conn.Get(path) → bytes + version
  3. Unmarshal into topodatapb.Shard (a protobuf)
  4. Wrap in ShardInfo (carries version for optimistic updates)
Version + lock = safe writes
Updates go through UpdateShardFields, which reads, mutates, and writes-if-version-unchanged. This is how Vitess avoids torn writes across vtctld instances.

Locks

// e.g. in vtctld during a reparent
ctx, unlock, err := ts.LockShard(ctx, keyspace, shard, "reparent")
if err != nil { return err }
defer unlock(&err)
// ... mutate shard records ...
  • Locks are advisory but enforced by convention across vtctld & vtorc.
  • Backed by the topo's primitive (etcd lease, ZK ephemeral node).
  • If holder dies, lease expires.

See go/vt/topo/locks.go, go/vt/topo/shard_lock.go.

Watches: how vtgate stays current

  • vtgate doesn't poll topo on every query — that would melt etcd.
  • It watches SrvKeyspace and SrvVSchema. Topo pushes deltas.
  • Local cache served, refreshed on watch events.
  • go/vt/srvtopo/ — the read-through cache layer on top of topo.
When you change vschema
Updates flow: vtctldclient → global topo → topo replicates to cell → vtgate watch fires → cache refresh. Sub-second normally, but not instant.

Inspecting topo from the CLI

# list keyspaces
vtctldclient GetKeyspaces

# list shards

# list tablets
vtctldclient GetTablets --keyspace commerce

# read the vschema
vtctldclient GetVSchema commerce

And if you really want to see raw bytes (debug only):

etcdctl --endpoints=http://localhost:2379 get --prefix /

Checkpoint quiz

1. The same shard record could be modified by two vtctlds at once. How does topo prevent the lost update?
Reveal
Every Get returns a version. Updates are conditional: "write iff version is X". One of the two updates fails the version check and retries. This is optimistic concurrency control — same idea as etcd revisions.
2. Why does vtgate watch SrvKeyspace instead of polling it?
Reveal
Polling would either melt etcd or be slow to react to changes. Watches push deltas. vtgate caches locally and refreshes on watch events.
3. Where are tablet records stored — global or cell-local?
Reveal
Cell-local. Each cell knows about its own tablets. Global topo holds cluster-wide things: keyspaces, vschema, locks.
