The Primitive interface

// in go/vt/vtgate/engine/primitive.go (abridged)
type Primitive interface {
    GetTableName() string
    RouteType() string

    Execute(ctx context.Context, vcursor VCursor,
        bindVars map[string]*querypb.BindVariable, wantfields bool) (*sqltypes.Result, error)

    StreamExecute(ctx context.Context, vcursor VCursor,
        bindVars map[string]*querypb.BindVariable, wantfields bool,
        callback func(*sqltypes.Result) error) error

    GetFields(ctx context.Context, vcursor VCursor,
        bindVars map[string]*querypb.BindVariable) (*sqltypes.Result, error)

    Inputs() ([]Primitive, []map[string]any)
    NeedsTransaction() bool
}

Every primitive — Route, Join, Aggregate — implements this. Tree composes by primitives holding their inputs.

Route — the leaf primitive

  • Holds: a parameterized SQL string + which shards to send it to.
  • Shards may be: all (scatter), one (selected by vindex), or any one (rdonly queries).
  • Calls vcursor.ExecuteMultiShard, which goes through scatter_conn.go.
type Route struct {
    Opcode RouteOpcode
    Keyspace *vindexes.Keyspace
    TargetDestination key.Destination
    Query string  // parameterized
    FieldQuery string  // for GetFields
    Vindex vindexes.Vindex
    Values []evalengine.Expr
    // ...
}

RouteOpcode: how to pick shards

OpcodeMeaning
UnshardedOne unsharded keyspace, one shard
EqualUniqueWHERE col = N, where col has a unique vindex
EqualSame, non-unique vindex (may hit multiple shards)
INWHERE col IN (...) → potentially multiple shards
ScatterNo vindex predicate — hit all shards
ReferenceReference table; any shard works
NoneProvably zero shards (e.g. WHERE 1=0)

The opcode controls which shards Route dispatches to at runtime.

Join primitive

type Join struct {
    Opcode JoinOpcode  // Inner, Left
    Left   Primitive
    Right  Primitive
    Cols   []int      // -col = from left; +col = from right
    Vars   map[string]int  // bind-var name → column from left
}
  • Executes left, then for each left row sets bind vars, executes right.
  • "Naive join" — works because plans only emit it when nothing better exists.
  • Hot path code: go/vt/vtgate/engine/join.go · Execute

HashJoin

  • Build a hash of one side, probe with the other.
  • Used when the join is between two large multi-shard subqueries.
  • Memory cost goes up; cross-shard latency goes down.
  • go/vt/vtgate/engine/hash_join.go

Aggregation primitives

  • ScalarAggregate — SUM(*), COUNT(*), no GROUP BY → one row out.
  • OrderedAggregate — input already sorted by GROUP BY cols; stream-aggregate.
  • Aggregate — generic, hash-aggregate fallback.
  • Often the planner pushes a partial aggregate into each Route and combines at vtgate.
Two-step aggregation
SUM(x) across shards: each shard returns partial_sum; vtgate sums the partials. AVG(x) is harder — needs SUM+COUNT and divides post-aggregate.

ScatterConn: the fan-out

  • go/vt/vtgate/scatter_conn.go
  • Given (keyspace, shards, query, bindvars) → fire off N parallel RPCs, collect results.
  • Each shard is independently retried on transient errors.
  • If any shard's failure is final, the whole scatter fails (or returns partial if streaming).
qr, errs := scatterConn.Execute(ctx, sql, bindVars,

Discovery & HealthCheck

  • go/vt/discovery/healthcheck.go — vtgate (and others) maintain a healthcheck stream from each tablet.
  • For a given (keyspace, shard, tablet-type), discovery returns sorted candidates by replication lag + serving state.
  • The "least-lagged healthy tablet" wins.

Transactions across shards

  • vtgate keeps a SafeSession per client connection.
  • On first write to a shard inside a transaction, it issues Begin to that vttablet and remembers the txn id.
  • On COMMIT: vtgate calls Commit on every participating shard sequentially.
  • If a commit fails mid-way: partial commit (default) or 2PC if enabled.

go/vt/vtgate/tx_conn.go

The buffer (during reparents)

  • go/vt/vtgate/buffer/ — holds writes for a few seconds during a known reparent.
  • Triggered by: vtorc/vtctld broadcasting "shard primary moving"; healthcheck observing primary gone.
  • If reparent finishes within the window, queued requests re-execute against the new primary. Most clients never notice.

Recap of Part III

  • vtgate is a Go program with five hot paths: parse, plan, route, execute, stream.
  • The planner is generated logic on top of a small operator algebra.
  • The engine is a few dozen small primitives wired together by plans.
  • The scatter conn does the actual network work, with retries and discovery.

Checkpoint quiz

1. A Join primitive over two routes executes how?
Reveal
Execute the left route, then for each row, set bind vars and execute the right route. It's a "nested loop join". Cheap when the left side has few rows; expensive when it doesn't (HashJoin then wins).
2. How does Vitess turn a scatter SUM across N shards into one result?
Reveal
Planner pushes SUM(x) into each Route — every shard returns a partial sum. A ScalarAggregate primitive at vtgate sums the partials.
3. Two shards return errors during a scatter. What does vtgate do?
Reveal
If both errors are retriable (e.g. transient tablet unavailable), it retries. If one is final, the whole scatter fails with that error. Partial success doesn't bubble up to the client.
