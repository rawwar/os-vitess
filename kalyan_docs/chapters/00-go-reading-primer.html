Go, just enough to read.

Vitess is about ninety-five percent Go. Good news: Go is a small language. Even better news: reading Go is dramatically easier than writing it. This chapter teaches the patterns that appear in every Vitess file, with concrete examples you can match against real code.

What this chapter gives you

By the end of this chapter, you will
  • Open any Vitess Go file and identify its package, imports, types, and functions in 30 seconds.
  • Recognize structs, interfaces, and methods — and connect interfaces to their implementations.
  • Skim past Go's noisy error-handling boilerplate while still reading what matters.
  • Recognize goroutines, channels, and context.Context usage without panicking.
  • Find the entry point of any Vitess binary in well under a minute.

Don't try to memorize Go's syntax. Pattern-match. Most Go code you'll meet in Vitess uses a small repertoire of forms over and over.

The shape of a Go file

Every Go file in Vitess follows the same top-down order: package declaration, imports, types, functions. Once you've seen one, you can predict where everything will be in the next.

// every file starts with the package it belongs to
package vtgate

// then imports, grouped (stdlib first, then 3rd party, then local)
import (
    "context"
    "fmt"

    "github.com/spf13/pflag"

    "vitess.io/vitess/go/vt/log"
)

// then types (structs, interfaces, type aliases)
type Executor struct {
    // fields
}

// then functions and methods
func NewExecutor(...) *Executor { ... }
func (e *Executor) Execute(...) error { ... }

The import block tells you a lot before you read a single function. Stdlib imports (context, fmt, io, etc.) suggest what kind of file this is. Third-party imports (github.com/spf13/pflag) tell you which external libraries are in play. Local imports starting with vitess.io/vitess/... tell you which other Vitess packages this file depends on — usually the answer to "where do I look next?" lives there.

Packages: one directory equals one package

In Go, all .go files in a single directory belong to the same package. They share state without needing to import each other. The package name usually matches the directory name (with hyphens and digits removed).

  • go/vt/vtgate/ contains dozens of .go files all declaring package vtgate. They can freely call each other's functions.
  • Other packages import "vitess.io/vitess/go/vt/vtgate" and refer to its exported names as vtgate.Foo.
  • Subdirectories are different packages: go/vt/vtgate/engine/ declares package engine, and other code imports it as vtgate/engine.
Quick navigation trick
When you see engine.Plan in a Vitess file, that's the Plan type from the engine package. Look at the file's import block to find the full path (vitess.io/vitess/go/vt/vtgate/engine), strip the prefix, and you have a directory to jump to. This trick alone speeds up code reading enormously.

Structs: data containers

A struct is just a named record — a collection of fields with types. The shape is exactly what a row in a SQL table looks like.

type Customer struct {
    ID        int
    Email     string
    Country   string
}

c := Customer{ID: 1, Email: "alice@example.com", Country: "US"}
fmt.Println(c.Email)

Field names that start with an uppercase letter are exported — visible to other packages. Lowercase field names are private to the package. The same rule applies to type names, function names, and method names. This is Go's "no public/private keywords; capitalization is the access modifier" convention. Once you know it, you can skim any struct and instantly see what's the public API and what's internal.

type Executor struct {
    serv      srvtopo.Server  // unexported, package-private
    Resolver  *Resolver       // exported — other packages can use
}

Methods: functions attached to types

A method is a function with an extra receiver that names the type it belongs to. The receiver appears in parentheses between func and the method name.

// The (e *Executor) part is the receiver — what the method is attached to.
func (e *Executor) Execute(ctx context.Context, sql string) (*Result, error) {
    // ...
}

// Call it like this:
result, err := e.Execute(ctx, "SELECT 1")

Two flavors of receiver, and the difference matters when you read code:

  • (e *Executor) — pointer receiver. The method operates on the original Executor. It can modify the struct's fields. Almost everything in Vitess uses pointer receivers.
  • (e Executor) — value receiver. The method operates on a copy. Modifications stay inside the method. Common for small immutable types like time.Time.

Methods on different types can share names without conflict — (e *Executor) Close() and (c *Conn) Close() are two distinct functions. This is how Go gets "polymorphism" without classes.

Interfaces: "anything with these methods"

An interface is a named set of method signatures. Here's an example from Vitess:

type QueryService interface {
    Execute(ctx context.Context, sql string) (*Result, error)
    Begin(ctx context.Context) (int64, error)
    Commit(ctx context.Context, txID int64) error
}

Any type that has all three of those methods automatically implements QueryService — no implements keyword, no explicit declaration. This is called "structural typing" and it's one of Go's most useful features.

Why it matters for Vitess: the project uses interfaces to swap real components with fakes. QueryService has a real gRPC-backed implementation, but tests use a fake one (sandboxconn) that satisfies the same interface. Callers never know the difference. When you read code that takes a QueryService, look for the variable name to guess which implementation runs — but trust that the interface is the contract.

Spot the assertion
Sometimes you'll see var _ QueryService = (*RealQueryService)(nil) at the top of a file. That's a compile-time assertion: it forces the compiler to fail if RealQueryService ever stops satisfying QueryService. Useful when an interface gets a new method — the assertion shows you where to update.

Errors: Go's most-criticized feature

Go has no exceptions. Functions that can fail return an extra error value, and callers check it after every call. This is the famous "noisy" Go style:

result, err := db.Query("SELECT 1")
if err != nil {
    return nil, vterrors.Wrapf(err, "query failed for user %s", userID)
}
// ... use result ...

other, err := otherCall()
if err != nil {
    return nil, vterrors.Wrap(err, "otherCall failed")
}

It looks repetitive because it is. The trade-off is that you can't accidentally swallow an error — every error path is in your face. Vitess wraps errors with vterrors.Wrapf to add context as they bubble up; by the time an error reaches the user, it has a trail of "what was happening when this failed".

When you read code, train yourself to skim past the error-handling lines on first pass. The interesting logic is between them. Once you've understood the happy path, come back and read what each error case does — sometimes it's a retry, sometimes it's a transformation, sometimes it's a metric increment.

context.Context — the deadline carrier

Almost every long-running function in Vitess takes a ctx context.Context as its first argument. The ctx carries:

  • A deadline — how long this call may run before being cancelled.
  • A cancellation signal — if the caller stops caring (client disconnected, timeout fired), the signal propagates downstream.
  • Values — caller identity, trace IDs, request-scoped metadata.
func (e *Executor) Execute(ctx context.Context, sql string) (*Result, error) {
    ctx, cancel := context.WithTimeout(ctx, 30 * time.Second)
    defer cancel()
    // ... pass ctx to every downstream call ...
}

The defer cancel() idiom ensures resources are released when the function exits, no matter how. This pattern is everywhere in Vitess.

When you read code, the presence of ctx is a hint: this is a network or long-running operation, and it can be cancelled. The absence of ctx is a hint: this is pure computation or in-memory work, and it can't be interrupted from outside.

Goroutines and channels: cheap concurrency

Prefix any function call with go and it runs in a new goroutine — a lightweight thread of execution. Vitess routinely runs thousands at a time without breaking a sweat.

for _, shard := range shards {
    go executeOnShard(ctx, shard, query)
}

The catch: that loop doesn't wait for any of the goroutines to finish. To collect results you need a synchronization tool. The two most common in Vitess are sync.WaitGroup (for "wait until all of these finish") and channels (for "send me each result as it arrives").

results := make(chan *Result, len(shards))
for _, shard := range shards {
    go func(s string) {
        r, _ := executeOnShard(ctx, s, query)
        results <- r          // send into the channel
    }(shard)
}
for i := 0; i < len(shards); i++ {
    r := <-results            // receive from the channel
    combine(r)
}

Channels are typed: chan *Result only carries *Result values. The arrow tells you direction — ch <- value sends, x := <-ch receives. When you see a channel of an empty struct (chan struct{}), it's a signal channel — just for notification, no data.

Pointers, briefly

You'll see * everywhere. There's only one rule to internalize:

c := Customer{ID: 1}
p := &c                   // p is a pointer to c
fmt.Println(p.Email)      // Go auto-dereferences — same as (*p).Email
p.Email = "alice@b.com"   // modifies c through p
  • &c means "address of c". You get a pointer.
  • *p means "the value p points at". You rarely need to write this — Go auto-dereferences in most contexts.
  • In a parameter or return type, *Foo means "pointer to a Foo". Treat it like a JavaScript object reference.

When should code use a pointer? Usually when the value is large, when the function needs to modify the original, or when you want to express "this might be missing" (with nil). Vitess strongly prefers pointers for any non-trivial struct.

What to skip on first pass

Go has a few features that show up less often in Vitess and that you can safely defer learning:

  • Generics (func Map[T any](...)) — used sparingly. Mentally substitute "works for any type" and move on.
  • select with multiple cases — this is coordination logic for channels. Read the comments; come back to the details later.
  • Reflection (reflect.Value) — only in serialization-heavy code. Read at the function-signature level.
  • Build tags (//go:build linux) — different code paths for different OSes. Pick the file matching your OS and read that one.
  • cgo (import "C") — Vitess uses it rarely. Skip these files unless you specifically need them.

None of these block you from understanding most of the code. They become useful later, after you have the big picture.

A complete example to anchor everything

Here's a small but realistic Go program that uses every concept above:

package main

import (
    "context"
    "fmt"
    "time"
)

// Type definition — a struct with two fields, both exported.
type Customer struct {
    ID    int
    Email string
}

// Method with a pointer receiver. Returns a derived string.
func (c *Customer) Greet() string {
    return fmt.Sprintf("hello, %s", c.Email)
}

// Function that can fail. Notice ctx first, error last.
func getCustomer(ctx context.Context, id int) (*Customer, error) {
    if id <= 0 {
        return nil, fmt.Errorf("invalid id %d", id)
    }
    return &Customer{ID: id, Email: "alice@example.com"}, nil
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    c, err := getCustomer(ctx, 1)
    if err != nil {
        fmt.Println("error:", err)
        return
    }
    fmt.Println(c.Greet())
}

Walk through it: a struct (Customer), a pointer-receiver method (Greet), a function that returns (*Customer, error) (the standard Go shape), a main that creates a context with timeout, calls the function, checks the error, and calls the method. Every Vitess file is a variation on this — just bigger, with more types and more layers.

Patterns you'll see again and again

A small vocabulary of idioms covers most of what's interesting in Vitess code:

PatternWhat it means
defer cancel()Run cancel() when this function exits (regardless of how).
defer wg.Wait()Block until all goroutines in this WaitGroup finish.
select { case <-ctx.Done(): ... }Wait for cancellation; ctx.Done() fires when the context is cancelled.
var _ Iface = (*Impl)(nil)Compile-time check that Impl satisfies Iface.
sync.Mutex / RWMutexLock for thread-safe shared state.
atomic.Int64Lock-free integer counter.
chan struct{}A signal channel — used for notification, never carries data.

If you see something else weird, search gobyexample.com for the syntax. It's the fastest way to look up "what does this Go thing do".

Lab: find a Vitess entrypoint

15 min · read only, no running
  1. Open go/cmd/vtgate/vtgate.go in your editor. Notice it's tiny — under 30 lines.
  2. Find which package it declares and which other packages it imports.
  3. The main() function does almost nothing — it delegates to a CLI helper. Find that file: go/cmd/vtgate/cli/cli.go (or similar).
  4. Read the CLI file. Stop when you reach cobra.Command setup. That's where command-line flags are declared.
  5. Now repeat for go/cmd/vttablet/vttablet.go. Notice the shape is identical.
What to take away
Every Vitess binary follows the same shape: a tiny main in go/cmd/<binary>/, a cli sub-package that wires up cobra commands, and the actual logic in go/vt/<subsystem>/. You'll see this pattern in vtgate, vttablet, vtctld, vtorc — every long-running binary. This means: to learn what binary X does, start at go/cmd/X/X.go and follow the imports.

Checkpoint quiz

1. What's the difference between Email string and email string on a struct field?
Reveal
Capital Email is exported — visible outside the package. Lowercase email is private to the package. Same convention applies to functions, types, and methods. Capitalization is Go's access modifier.
2. When you see func (e *Executor) Execute(...), what does the * tell you?
Reveal
It's a pointer receiver — the method can read and modify the Executor it's called on. Without the * it would be a copy and modifications wouldn't stick.
3. Why does almost every Vitess function take ctx context.Context as its first parameter?
Reveal
Cancellation, deadlines, and tracing propagate through it. If the caller times out or the client disconnects, every downstream call learns about it via the same ctx.
4. go someFunc() — what's go doing?
Reveal
It starts someFunc in a new goroutine — a lightweight concurrent thread of execution. The caller doesn't wait for it to finish.
5. var _ QueryService = (*sandboxConn)(nil) — what's this idiom doing?
Reveal
It's a compile-time assertion that sandboxConn implements the QueryService interface. If anyone removes a method from sandboxConn that QueryService requires, compilation fails right at this line — fast feedback instead of mysterious runtime errors.
