Part I · Chapter 7

Why Vitess exists.

A single MySQL server can absolutely run your startup. The trouble starts when you outgrow it — and that's a much harder problem than it sounds.

Learning objectives

By the end of this chapter, you will
  • Describe the four ways MySQL stops scaling (writes, storage, ops, schema).
  • Compare the "obvious" scaling alternatives and what each costs.
  • Sketch Vitess's shape (apps → vtgate → vttablet → mysqld) on a napkin.
  • Decide when Vitess is and isn't worth it.

The problem in one sentence

"I want MySQL semantics, but I want my data to be 100× bigger and my traffic 1000× higher than one machine can handle."
  • MySQL on one box: rock solid, well understood, decades of tooling.
  • MySQL on a thousand boxes: who owns failover? who routes queries? who reshards live data?
  • Vitess is the answer to those whos — without making you rewrite your app to use a different database.

How big does Vitess scale?

  • Built at YouTube starting 2011 — eventually tens of thousands of MySQL instances.
  • Now in production at Slack, Block (Square), GitHub, Shopify, JD.com, etc.
  • Slack famously moved their entire database tier to Vitess.
Don't confuse "big" with "needed"
Most apps will never reach Vitess scale. Vitess is interesting because it solves a problem you probably don't have — yet. Learning it teaches you a lot about distributed databases regardless.

What "doesn't scale" means in MySQL

  • Write throughput — one primary takes all writes. Replicas help reads, not writes.
  • Storage — eventually the working set exceeds RAM and indexes blow past disk.
  • Operational blast radius — when "the database" is one machine, every cron job, ALTER, backup, etc. fights everyone else.
  • Schema changes — running ALTER TABLE on a multi-TB table is downtime.

shard N)]
  • App still speaks plain MySQL. Vitess pretends to be one big MySQL.
  • Behind the curtain: many real MySQLs, each owning a slice of the data.
  • Routing, failover, reshards, online schema migrations — all handled for you.

What Vitess gives you

  • Sharding without app changes. Your app issues normal SQL; Vitess figures out which shard(s) to hit.
  • Cross-shard queries. Joins, aggregates, scatter-gather all happen for you (within limits).
  • Online resharding. Split or merge shards while traffic flows. No write downtime.
  • Online DDL. ALTER TABLE on huge tables, no downtime.
  • Automatic failover. VTOrc watches replication; promotes a new primary on failure.
  • Workflow tooling. MoveTables, materialize, vdiff, backups, audits.

What Vitess costs you

  • Operational complexity. You now run vtgate, vttablet, vtctld, vtorc, a topo service, plus the MySQLs.
  • Query restrictions. Not every SQL feature works the same — joins across shards have rules, transactions across shards need 2PC.
  • Mental load. Sharding-by-key is a one-way commit. Pick the wrong key, pay the cost.
  • This tutorial. ~8 hours just to understand it.
When NOT to use Vitess
Less than ~1TB working set, less than ~10k QPS, no plans to scale 10×? You almost certainly don't need it. Use plain MySQL and replicas, profile, optimize.

The four pillars (preview of Parts III-V)

vtgate

Stateless proxy. Parses SQL, plans, routes to the right shard(s), aggregates results.

vttablet

Sits in front of each mysqld. Query rewriting, connection pool, schema, transactions, replication health.

vtctld / vtctldclient

The control plane: cluster admin commands, workflows.

topo

Configuration store (etcd, ZK, consul). Where shards, tablets, vschema live.

Checkpoint quiz

1. Vitess sits in front of "real" MySQLs. What does that imply about the data format on disk?
Reveal
It's vanilla InnoDB on disk. Any DBA who knows MySQL can debug a Vitess shard at the mysqld level. That's a deliberate design choice — it preserves 25 years of MySQL tooling.
2. What's the single biggest cost of using Vitess?
Reveal
Operational complexity. You now run 5+ kinds of process (vtgate, vttablet, vtctld, vtorc, topo) plus the MySQLs. If you don't actually need scaling, this is overhead for no payoff.
3. Name two things that change once your transaction touches more than one shard.
Reveal
(a) Default semantics become per-shard atomic, not globally atomic — you can have a partial commit. (b) Joins across shards are coordinated by vtgate at extra cost. Many apps choose a shard key that keeps related rows together to avoid both.
