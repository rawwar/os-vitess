Part III · Chapter 18

Vitess has its own SQL parser.

Yacc-generated, hand-tuned to match MySQL closely. The AST it produces is the lingua franca of vtgate.

Learning objectives

By the end of this chapter, you will
  • Tell apart the source files (ast.go, sql.y) from the generated ones.
  • Read a SELECT's AST shape from the Select struct.
  • Recognize Walk, SafeRewrite, Normalize, and Clone as the four operations on ASTs.
  • Know what to do (and not do) when adding a new AST node.

Why a custom parser?

  • vtgate needs to rewrite SQL (e.g. add shard hints, push down filters). Reusing MySQL's parser means embedding C++.
  • A Go parser lets Vitess walk, transform, and re-print SQL freely.
  • The MySQL community has fragmented dialects (Aurora, Percona, MariaDB) — Vitess's parser tries to be the lowest common denominator.
  • Originally forked from YouTube/vitess and continually expanded.

Two layers, one package

  • go/vt/sqlparser/sql.y — the yacc grammar. Source.
  • go/vt/sqlparser/sql.go — generated parser. Don't edit.
  • go/vt/sqlparser/ast.go — handwritten AST node definitions.
  • go/vt/sqlparser/ast_funcs.go — handwritten AST methods.
  • Generated walkers/cloners/formatters live in ast_clone.go, ast_equals.go, ast_visit.go, etc.

Calling the parser

// Two flavors
stmt, err := sqlparser.Parse("SELECT * FROM customer WHERE id = 1")

// "Parse2" returns reserved-variable accounting (for binds)
stmt, reservedVars, err := sqlparser.Parse2("SELECT * FROM customer WHERE id = ?")

Returns an sqlparser.Statement (an interface). Switch on the concrete type:

switch s := stmt.(type) {
case *sqlparser.Select: // ...
case *sqlparser.Insert: // ...
case *sqlparser.Update: // ...
case *sqlparser.DDL:    // CREATE/ALTER/DROP
}

Walkers: Walk & SafeRewrite

// Visit every node
err := sqlparser.Walk(func(node sqlparser.SQLNode) (kontinue bool, err error) {
    if col, ok := node.(*sqlparser.ColName); ok {
        fmt.Println("column:", col.Name.String())
    }
    return true, nil
}, stmt)

// Rewrite while walking
result := sqlparser.SafeRewrite(stmt, nil, func(cursor *sqlparser.Cursor) bool {
    if lit, ok := cursor.Node().(*sqlparser.Literal); ok && lit.Type == sqlparser.IntVal {
        cursor.Replace(sqlparser.NewIntLiteral("42"))
    }
    return true
})

Both are generated from AST struct definitions. Field order in the struct controls visit order — don't reorder casually.

Formatting back to SQL

// Re-print the AST as SQL
buf := sqlparser.NewTrackedBuffer(nil)
buf.Myprintf("%v", stmt)
result := buf.String()

// or use the fast path:
result := sqlparser.String(stmt)
  • ast_format.go — handwritten, used when you need full control.
  • ast_format_fast.go — generated, optimized.

Round-tripping isn't guaranteed byte-perfect — comments and whitespace can move.

Normalization & bind variables

// Replace literals with bind vars (for plan cache reuse)
stmt, reservedVars, err := sqlparser.Parse2(sql)
sqlparser.Normalize(stmt, reservedVars, bindVarsOut)
// SELECT * FROM t WHERE id = 1 AND name = 'kalyan'
// →
// SELECT * FROM t WHERE id = :vtg1 AND name = :vtg2
go/vt/sqlparser/normalizer.go
  • This is how vtgate gets plan cache hits across queries that only differ in literal values.
  • Bind vars also block SQL injection at the boundary.

Cloning & equality

  • go/vt/sqlparser/ast_clone.go — Clone(node), deep copy. Generated.
  • go/vt/sqlparser/ast_equals.go — Equals.SQLNode(a, b). Generated.
  • Both are crucial for the planner — it builds candidate plans by mutating clones and compares plans for equality during deduplication.

Adding a new AST node — the recipe

  1. Add the struct to ast.go.
  2. Add handwritten methods to ast_funcs.go (constructor, optional helpers).
  3. Add grammar rules in sql.y that produce the new node.
  4. Run make codegen — regenerates sql.go, walkers, cloners, formatters, cached_size.
  5. Add a test case under go/vt/sqlparser/testdata/ (look at existing JSON files for the format).
Field order matters
Generated walkers visit fields in declaration order. If your new field needs to be visited before something else (e.g. you set up scope before resolving names), put it first.

Other parser-related files

  • comments.go — /* vt+ ... */ hint comments
  • keywords.go — reserved keywords table
  • analyzer.go — quick "what kind of statement is this" (without full parse, for SQL routing fast path)
  • parsed_query.go — pre-parsed query you can substitute bind vars into cheaply
  • literal.go — value parsing

The running example, parsed

Our query SELECT c.customer_id, c.email FROM customer c WHERE c.customer_id = 42 becomes a *sqlparser.Select with roughly:

Select {
  SelectExprs: [c.customer_id, c.email]
  From: [AliasedTableExpr{Expr: TableName{Name:"customer"}, As:"c"}]
  Where: &Where{
    Type: "where",
    Expr: ComparisonExpr{
      Operator: "=",
      Left:  ColName{Qualifier:"c", Name:"customer_id"},
      Right: Literal{Type: IntVal, Val: "42"},
    },
  },
  Limit: nil,
  ...
}

Notice: 42 is still a literal. Normalization will replace it with a bind variable before plan caching, so the plan for id = 42 is reused for id = 99.

Checkpoint quiz

1. Why does Vitess maintain its own parser instead of reusing MySQL's?
Reveal
MySQL's parser is C++ inside mysqld. Vitess needs to rewrite SQL (push down filters, normalize literals, route by vindex). A pure-Go parser with a walkable AST makes that easy.
2. You add a new field to the Select struct in ast.go. What else must you do?
Reveal
Run make codegen. It regenerates ast_clone.go, ast_equals.go, ast_visit.go, ast_format_fast.go, cached_size.go. Field order matters — walkers visit in declaration order.
3. After Normalize, what does WHERE id = 42 AND name = 'a' look like?
Reveal
Roughly: WHERE id = :vtg1 AND name = :vtg2, plus a bind-vars map {"vtg1": 42, "vtg2": "a"}. That's how the plan cache stays small.
