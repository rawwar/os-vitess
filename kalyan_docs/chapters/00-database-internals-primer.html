What's inside a database?

Before we read any MySQL or Vitess code, let's build a mental picture of what every relational database is doing under the hood. This is the picture every later chapter will keep referring back to.

What this chapter gives you

By the end of this chapter, you will
  • Trace the path from "client SQL" to "rows on disk" in five clear steps.
  • Picture how a tree-shaped index makes lookups O(log N).
  • Explain locks, isolation, MVCC, and why long transactions hurt everyone.
  • Define replication, name its two failure modes, and counter the "a replica is a backup" misconception.

The next chapter (Go primer) is a tool break. After that, we cross into MySQL specifics. Everything below applies just as much to PostgreSQL or SQLite — and that's the point: most database mental models are portable.

The big picture

Every relational database is, at a slightly cartoonish level, the same five-box pipeline. Bytes come in over the network, get parsed and planned and executed, and rows come back out. Storage of the actual data is its own world, talked to via an internal API.

flowchart LR Client[client] -->|SQL over network| Server[server process] subgraph DBProcess [database process] Parser[parse] Planner[plan] Exec[execute] Storage[storage engine] Buffer[buffer pool · RAM] end Server --> Parser --> Planner --> Exec --> Storage Buffer <--> Storage Storage --> Disk[(data files on disk)]

You'll see this pattern again in vtgate: SQL comes in, gets parsed, planned, executed — except instead of touching disk, vtgate's "executor" sends RPCs to vttablets. The shape is so similar that reading go/vt/vtgate/executor.go feels uncannily like reading a tiny standalone database.

Of the five boxes, the one most worth understanding deeply is the storage engine — because that's where the disk-shaped reality lives. The parser/planner/executor are about translating SQL into operations; the storage engine is where pages get read, locks get held, and durability gets guaranteed.

Pages: rows never sit alone

Disks read and write in chunks, not bytes. The database doesn't fetch one row at a time; it fetches one page — typically 16 KB in MySQL/InnoDB, 8 KB in PostgreSQL. A page holds many rows, plus some bookkeeping.

flowchart TB page["Page (16 KB)"] page --> r1["row 1: id=1, alice@..."] page --> r2["row 2: id=2, bob@..."] page --> r3["row 3: ..."] page --> rest["...up to ~100 rows"]

One consequence: a single-row lookup costs at least one full page read. The other rows in that page came along for free — if you happen to need them soon, they're already in the buffer pool (the in-memory page cache). That's why range scans on a clustered index are cheap: each page contains many adjacent rows.

Another consequence: if your rows are large (say, you stored 4 KB of JSON in each), pages hold fewer rows, range scans get slower, and the buffer pool's hit rate drops. Database performance often comes down to "fit more useful data per page".

Indexes as trees

To find a value without scanning every row, the database needs the data sorted. An index keeps the indexed column's values in a tree where each lookup is a few comparisons.

To find customer_id = 42: compare to the root node's keys, pick a branch; compare to the child node's keys, pick again; repeat until you reach a leaf, which points at the row. For a billion rows, this takes about four or five hops. That's the entire performance promise of relational databases — without it, everything would be linear scans.

"B+ tree" is just a particular sorted tree
Every relational database uses some variant of a B-tree. MySQL/InnoDB uses a B+ tree with a twist: the primary key index stores the rows themselves at its leaves (a "clustered" index). Secondary indexes store the primary key value at their leaves, which means a secondary-index lookup followed by a row fetch is actually two B+ tree lookups — first into the secondary index, then into the primary.

This detail will matter in chapter 8 when we talk about why a primary key choice in MySQL has knock-on effects for every other index on the table. It also matters for Vitess: when Vitess picks a sharding key, it's usually picking the column most queries filter by — which is also typically the primary key.

Concurrency: two writers, one row

What happens when Alice and Bob simultaneously try to add $50 to the same bank balance? Without coordination, this:

sequenceDiagram participant A as Alice participant B as Bob participant DB as DB A->>DB: read balance (100) B->>DB: read balance (100) A->>DB: write balance = 150 B->>DB: write balance = 150 Note over DB: lost $50!

Both reads saw 100. Both writes set 150. The bank lost $50. This is a race condition, and any database used for real money has to prevent it. The fix is locking: whichever writer grabs the row first holds an exclusive lock; the other waits until the first commits.

Locks come in flavors. A shared (read) lock can be held by many readers at once but blocks all writers. An exclusive (write) lock blocks all readers and writers. Locks can apply at row level (cheap, granular) or at table level (rare, used for DDL). In InnoDB, almost all locks are row-level — which is why a busy update on one row doesn't paralyze the rest of the table.

Deadlocks
Two transactions can wait for each other's locks forever. T1 holds row A and wants row B; T2 holds row B and wants row A. Neither will ever release. InnoDB detects this within a few milliseconds, picks the "smaller" transaction, and aborts it with a Deadlock found when trying to get lock error. Your app's job is to retry the aborted transaction. Vitess preserves this behavior unchanged within a shard.

Isolation: how separate are transactions?

Even with locks, you need to decide what one transaction sees when others commit in the meantime. MySQL's default isolation level is REPEATABLE READ: each transaction gets a consistent snapshot of the database at the moment it starts, and reads return that snapshot regardless of concurrent commits. Writers don't block readers; readers don't block writers. This is implemented via MVCC (Multi-Version Concurrency Control).

The mechanism: InnoDB never overwrites a row in place. An UPDATE creates a new version of the row; the old version stays in the undo log, tagged with the transaction ID that wrote it. When a reader's snapshot would see the old version, InnoDB serves the old version from undo. When all transactions that need a given old version finish, the undo entry can be purged.

Most of the time you don't notice MVCC. You notice it when something goes wrong.

Long transactions hurt everyone
Every old row version lives in the undo log. A transaction open for hours forces InnoDB to keep an ever-growing pile of old versions for it. Concurrent writes pile on more. The undo log balloons; the buffer pool fills with rarely-used versions; performance falls off. In Vitess this is doubly bad: a long transaction at the app also holds a vtgate connection, which holds a vttablet pool slot, which holds the MySQL connection. CLAUDE.md is explicit about this: don't hold transactions open while you do slow work.

Crash recovery and the write-ahead log

Disks lose power. Kernels panic. The database has to guarantee that once it tells the client "your COMMIT succeeded," the data is durable even if the server vanishes a millisecond later. That guarantee is built on the write-ahead log (WAL).

The trick is to never write the actual data page first. Instead:

  1. Append the change description to a log file. Sequential writes to a single file are very fast — much faster than scattered page writes.
  2. Once the log entry is durable (the disk has acknowledged the write), tell the client "committed".
  3. Later, lazily flush the actual data pages from the buffer pool to their permanent locations.
  4. If the server crashes between steps 2 and 3, replay the log on startup. Every committed change is recovered.

In MySQL, this log is the redo log. InnoDB replays it during startup to bring the data files back up to the last committed transaction.

Three logs you'll meet

Beginners often conflate "logs" in MySQL because there are several of them and the names overlap. Here are the three that matter:

LogPurposeWho reads it
RedoCrash recoveryInnoDB itself, at startup
UndoRollback + MVCC old versionsInnoDB itself, during transactions
BinlogReplication & change feedOther MySQLs and Vitess

The redo log is physical (page-level), circular, and internal. The undo log is conceptually a list of "how to undo each change" entries. Both serve InnoDB internally and are not exposed to the outside world.

The binlog is different. It's a logical record of every row change (or every SQL statement, depending on format), written by the server layer above the storage engine. Its primary purpose is replication: other MySQLs read it to stay in sync with this one. Vitess uses it for the same reason and also for VReplication — copying rows between shards, materializing views, online schema changes. We'll spend chapter 9 on the binlog in detail.

Internalize this
The redo log keeps a single MySQL durable. The binlog keeps multiple MySQLs in sync. They sound similar; they serve different purposes. Vitess only cares about the second.

Replication: one DB, many copies

At its simplest, MySQL replication is one server (the primary) writing every change to its binlog, and other servers (the replicas) opening a long-running connection to stream those events and replay them locally.

flowchart LR primary[(primary)] -->|stream of binlog events| r1[(replica 1)] primary -->|stream of binlog events| r2[(replica 2)] primary -->|stream of binlog events| r3[(replica 3)]

Replicas serve reads — the app can route SELECTs to them to scale read throughput. If the primary dies, one of the replicas is promoted and starts accepting writes. Most of Vitess's automation is, ultimately, in service of making that promotion safe and fast.

Replication is asynchronous by default: the primary writes its binlog, acknowledges the COMMIT to the client, and only then do replicas pull the event. If the primary dies in that tiny window between "acknowledge COMMIT" and "replica receives event", that committed write is lost from the cluster's point of view. The window is small (milliseconds, usually) but not zero.

Replicas can lag, and semi-sync helps

Replicas can fall behind for many reasons: a slow disk, a heavy local read query stealing CPU, a long-running ALTER, simple network delay. Replication lag — measured in seconds-behind-primary — is the single most-watched metric in a MySQL ops dashboard.

Replicas can lag
A replica that's 10 seconds behind has 10 seconds' worth of writes still pending. If the primary dies, those writes don't exist on that replica. Some other replica might have them; some replica must be picked carefully to promote.

The fix for the worst version of this is semi-synchronous replication. With semi-sync turned on, the primary waits for at least one replica to acknowledge receipt of an event before saying "committed" to the client. The trade-off is latency — every commit now blocks on a network round-trip. The benefit is correctness: at least one replica has the data the primary acked. Vitess strongly encourages semi-sync because its failover logic (chapter 23) depends on it.

"A replica is a backup"
No. If you run DROP TABLE customer on the primary, it replicates to every replica within seconds. Replicas protect you against hardware failure, not human error. You still need point-in-time backups. We cover Vitess's backup story in chapter 30.

What this lets you do

You now have a working mental model of any relational database. Rows live in pages on disk. Indexes are trees that make lookups O(log N). Concurrent transactions use locks plus MVCC to avoid corrupting each other. A WAL makes the database crash-safe. The binlog feeds replicas and change consumers like Vitess.

From here, every chapter will refine and specialize this picture. Chapter 8 zooms into MySQL's InnoDB specifically. Chapter 9 zooms into the binlog and GTIDs. Chapter 25 layers sharding on top. You'll keep coming back to this picture in particular, so it's worth re-reading the diagrams above once before moving on.

Checkpoint quiz

1. Why does the database read 16 KB at a time even when you only asked for one row?
Reveal
A page is the unit of disk I/O. Reading less wouldn't be faster, because the underlying disk reads in blocks anyway. So MySQL packs ~100 rows into each page; if your next read is nearby, those rows are already in memory.
2. Replica X is 10 seconds behind the primary. The primary dies. Did we lose data?
Reveal
With vanilla async replication, yes — the last 10 seconds of committed writes are gone from this replica. With semi-sync replication, at least one replica is guaranteed to have every committed write; the question becomes which replica. Vitess's failover picks the most-advanced replica precisely for this reason.
3. Why is a replica not a backup?
Reveal
A replica copies every change — including destructive ones. DROP TABLE on the primary propagates to every replica within seconds. Replicas protect you from hardware failure; only point-in-time backups protect you from human error.
4. The redo log and the binlog both record changes. What's the difference?
Reveal
Redo is for crash recovery — replayed by the same MySQL on startup, physical (page-level), and never leaves the server. Binlog is for replication and external consumers — replayed by other MySQLs and by Vitess, logical (row or statement events), and explicitly designed to be consumed by other processes.
5. A transaction is open for four hours. Why does that hurt the entire MySQL, not just the slow caller?
Reveal
MVCC keeps old row versions in the undo log so the long transaction can still see its snapshot. Every concurrent write piles on more old versions. The undo log balloons; the buffer pool fills with old versions; performance degrades for everyone.
