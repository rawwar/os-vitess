Live data, moving.

MoveTables ships rows between keyspaces. Reshard splits or merges shards. Same VReplication engine, different shapes.

Learning objectives

By the end of this chapter, you will
  • Walk the workflow lifecycle (create → copy → catchup → vdiff → switch → complete).
  • Run a full MoveTables in the local example.
  • Understand why VDiff happens before switching traffic.
  • Know the difference between switchtraffic (reversible) and complete (final).

The lifecycle of a workflow

flowchart LR Create[create workflow] --> Copy[copy phase
RDONLY queries] Copy --> Catchup[catchup
tail binlog] Catchup --> VDiff[vdiff verify] VDiff --> SwitchR[switchtraffic
rdonly + replica] SwitchR --> SwitchW[switchtraffic
primary] SwitchW --> Complete[complete
or cancel]

Every workflow follows this shape. The only thing that changes is the source/target topology.

MoveTables: cross-keyspace copy

vtctldclient MoveTables \
    --workflow commerce2customer \
    --target-keyspace customer create \
    --source-keyspace commerce \
    --tables "customer,corder"
  • Source: all shards of commerce
  • Target: all shards of customer
  • For each target shard, one VReplication workflow pulls rows from each source shard that matches the new shard's keyrange.

Code path: go/vt/vtctl/workflow/server.go · MoveTablesCreate → builds the VReplication rows → calls each target tablet's CreateVReplicationWorkflow.

Reshard: same-keyspace split/merge

vtctldclient Reshard \
    --workflow cust2cust \
    --target-keyspace customer create \
    --source-shards '0' \
    --target-shards '-80,80-'
  • Source shard 0 (the whole range) → target shards -80 + 80-.
  • VReplication rows on each target shard tail the source shard's binlog.
  • Filter: WHERE keyspace_id IN this_target_range.

SwitchTraffic — the cutover

  1. switchtraffic --tablet-types "rdonly,replica" first.
    • Routes reads to the target.
    • Reversible — if you see issues, you can switch back.
  2. Confirm metrics look good.
  3. switchtraffic --tablet-types primary.
    • Briefly freezes writes on source primary.
    • Waits for VReplication to catch up (zero lag).
    • Flips routing rules in topo so writes go to target.
    • Sets source to read-only.
  4. If anything is wrong, reverse-traffic brings writes back.

The cutover, in code

  • go/vt/vtctl/workflow/server.go — main workflow logic.
  • go/vt/vtctl/workflow/switcher.go — the cutover state machine.
  • go/vt/vtctl/workflow/stream_migrator.go — moves existing VReplication streams across reshards.
  • Routing rules are updated in topo (RoutingRulesFile, ShardRoutingRulesFile).
  • vtgate's vschema watcher picks up the new rules and re-routes.

Complete vs cancel

  • Complete — workflow is permanent.
    • Stops VReplication streams.
    • For MoveTables: deletes source tables.
    • For Reshard: marks source shards inactive (you delete with DeleteShards).
  • Cancel — undo, source remains canonical.
Reversibility window
Between "switchtraffic primary" and "complete", the source is still in sync but read-only. That is your "if everything explodes, flip back" window. Don't complete until you're sure.

Reverse VReplication

  • After SwitchTraffic, Vitess automatically creates a reverse workflow.
  • Target binlog → Source mysqld. Keeps source warm in case you need to fall back.
  • Lives in _vt.vreplication on the source.
  • Removed by complete.

Routing rules in motion

Before switchtraffic, vtgate routes customer table queries to commerce.customer. After:

{
  "rules": [
    {
      "from_table": "commerce.customer",
      "to_tables": ["customer.customer"]
    }
  ]
}

So even if your app still writes commerce.customer, the query lands on the new keyspace.

Materialize

  • Long-running VReplication workflow that maintains a derived table.
  • Source: a SQL query. Target: a materialized view stored as a real table.
  • Use cases: denormalized reads, cross-shard aggregates, search indexes.
  • go/vt/vtctl/workflow/materializer.go

Worth knowing: throttler interplay

  • VReplication is throttled by the same engine used for online DDL.
  • If a primary mysqld is busy, the throttler tells VReplication to back off.
  • Lag can grow during throttle; usually catches up after.

Checkpoint quiz

1. Why does Vitess auto-create a reverse VReplication workflow on cutover?
Reveal
So you can roll back. Until you complete the workflow, the source still has live, in-sync data. If post-cutover monitoring spots a problem, reverse-traffic flips writes back to the source within seconds.
2. Why does SwitchTraffic for primaries briefly freeze writes?
Reveal
To wait for VReplication to fully drain the source binlog onto the target. Once the target is at the same GTID as the source, vtgate flips the routing rules. Total freeze is usually seconds.
3. What does VDiff actually do?
Reveal
Streams rows from both source and target in PK order, side-by-side, comparing each. Reports mismatches; never writes. Always run before complete.
