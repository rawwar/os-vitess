Part V · Chapter 29

The traffic cop.

VReplication and online DDL must not break production traffic. The throttler is the centralized "are we OK to do more work?" oracle.

Learning objectives

By the end of this chapter, you will
  • Explain what the throttler does in one sentence.
  • Name 3+ apps that check it (VReplication, online DDL, vstreamer, ...).
  • Probe a tablet's throttler via HTTP.

What it does

  • Watches a metric (replication lag by default).
  • If the metric exceeds threshold → "throttle now".
  • Background workloads (VReplication, online DDL, vstreamer, etc.) ask "am I throttled?" between batches.
  • If yes, they back off; if no, they continue.

It's an in-process service inside each vttablet, with cross-tablet awareness through topo.

The check loop

  1. Every N seconds, probe each replica's SHOW REPLICA STATUS.
  2. Compute Seconds_Behind_Source (or use heartbeat).
  3. If any replica exceeds threshold → mark "throttled".
  4. Clients see "throttled" on their next call until lag drops.

Heartbeat-based lag is more accurate than Seconds_Behind_Source (which is replica-clock-dependent).

Apps that check the throttler

  • vreplication — between row batches
  • online-ddl — between copy batches
  • vstreamer — when serving a VStream to a third party
  • vplayer — same engine, different role
  • tablegc — when dropping abandoned tables

Each "app name" can have its own threshold & rules.

The client API

// client.go (abridged)
type Client struct { /* ... */ }

func (c *Client) ThrottleCheckOK(ctx context.Context, app string) (bool, error)
func (c *Client) ThrottleCheckOKOrWaitAppName(ctx context.Context, appName ThrottlerAppName) error

Callers pause until the throttle clears. Code-style: check between batches, not inside them.

Tuning the throttler

Operators tune via vtctldclient:

vtctldclient UpdateThrottlerConfig \
    --enable --threshold 5s \
    --custom-query "SELECT 1 - SUM(lag) / 30 FROM heartbeat" \
    commerce
  • Threshold: max acceptable lag.
  • Custom query: replace the default lag probe with anything that returns a metric.
  • Per-app exemptions: e.g. let online DDL run even when VReplication is throttled.

Why per-tablet, not centralized?

  • Centralized throttler = single point of failure + 1 extra hop in every check.
  • Per-tablet means: when the local tablet is healthy, no network round-trip.
  • Cross-tablet info comes via topo (less frequent).

This is the Vitess design philosophy: keep the data plane local, push only the minimum coordination through topo.

The "self-check" endpoint

Each vttablet exposes:

curl http://<vttablet>/throttler/check?app=vreplication

Returns HTTP 200 if OK, 429 if throttled. Useful for debugging "why is my VReplication slow?".

Checkpoint quiz

1. The throttler is per-tablet, not centralized. Why?
Reveal
A centralized throttler would be a single point of failure and a network hop on every check. Per-tablet keeps the data plane local; topo carries the rare cross-tablet info.
2. Where do background apps check the throttler — inside their tight loop, or between batches?
Reveal
Between batches. Calling it on every row would dominate cost. Checking between, say, 1000-row chunks is plenty.
