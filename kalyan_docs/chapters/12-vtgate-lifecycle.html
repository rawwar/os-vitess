  • Calls go/vt/sqlparser/parser.go.

Step 2: plan

// Roughly:
plan, err := e.getPlan(ctx, vcursor, sql, stmt, bindVars, ...)
  • Cache lookup first — same SQL with same vschema version reuses a plan.
  • If miss: call go/vt/vtgate/planbuilder/planner.go · BuildFromStmt.
  • Result is an engine.Plan — a tree of primitives from go/vt/vtgate/engine/.

Sessions & transactions

  • The MySQL conn has a SafeSession: tracks InTransaction, charset, autocommit, system vars.
  • On BEGIN: session flips to InTransaction; subsequent statements join the existing txn(s).
  • If a statement touches a new shard, vtgate starts a txn there too (and remembers it).
  • On COMMIT: vtgate commits each shard. Per-shard atomic, cross-shard best-effort. (2PC opt-in.)
go/vt/vtgate/executorcontext/ · SafeSession

Streaming vs buffered

  • Buffered (Execute): collect all rows, return a sqltypes.Result. Simple, but memory-bounded by result size.
  • Streaming (StreamExecute): push partial results to a callback as they arrive. The MySQL listener uses this — it writes packets as rows come in.

Vitess prefers streaming for client-facing reads. Pulled into sqltypes.ResultStream internally.

Errors & retries

  • Tablet down? vtgate's discovery has alternates; the executor retries on a healthy replica.
  • Reparent in progress? The buffer (go/vt/vtgate/buffer/) holds writes briefly until the new primary is known.
  • Cross-shard partial failure with 2PC off? You get partial commit. Caller's responsibility.
Buffer is a feature, not a bug
For ~5 sec during reparents, vtgate will queue writes. Latency briefly spikes; correctness wins. Don't accidentally disable it.

Checkpoint quiz

1. The MySQL listener calls StreamExecute (not Execute). Why streaming by default?
Reveal
vtgate can start writing result packets to the client as soon as the first row arrives from a vttablet — no need to buffer the whole result in memory. For large reads this matters a lot.
2. Where is the per-connection state (e.g., "am I in a transaction?") stored?
Reveal
In the SafeSession attached to the MySQL connection's UserData. It tracks transaction state, charset, autocommit, system variables, and the shards already participating in the current transaction.
3. A vttablet briefly disappears mid-reparent. Does the client see an error?
Reveal
Usually no. vtgate's buffer package holds writes for up to a few seconds during a known reparent. If the new primary appears in time, the queued writes execute against it. Latency spikes briefly; correctness wins.
