Part I · Chapter 11

Pools, all the way down.

Every "connection" you see at the Vitess boundary is actually a leased slot from a pool. Knowing the layers protects you from the most common production foot-guns.

Learning objectives

By the end of this chapter, you will
  • Explain why a pool exists in one sentence.
  • Name vttablet's three pools and what each holds.
  • Recognize the symptoms of pool exhaustion in logs.
  • Trace a transaction's life through vtgate → vttablet → mysqld.

Why pools exist

  • Opening a TCP connection + handshake + auth costs ~1-5 ms. Per query, that's catastrophic.
  • MySQL has a hard cap (max_connections, default 151). Crossing it = "Too many connections" errors.
  • Pools amortize handshake cost and bound concurrency.
The Vitess invariant
Apps may open thousands of connections to vtgate. vtgate keeps a small bounded pool to each shard. Connection count amplification is exactly inverted — that's the headline value.

vttablet keeps three separate pools to its mysqld: read-only queries, transactions, and "DBA" (admin) work.

Generic pool primitives

  • go/pools/resource_pool.go — generic Get/Put pool with min/max size, idle timeout, wait queue.
  • go/pools/smartconnpool/ — newer "smart" pool tuned for DB connections (less lock contention, better metrics).
  • go/pools/numbered.go — pool of resources keyed by ID (used for active transactions).
  • go/pools/rpc_pool.go — RPC concurrency limiter.

The Resource interface

// In go/pools/resource_pool.go
type Resource interface {
    Close()
    Expired(lifetimeTimeout time.Duration) bool
    ApplySetting(ctx context.Context, setting *Setting) error
    IsSettingApplied() bool
    ResetSetting(ctx context.Context) error
    Setting() *Setting
}
  • Anything that can be pooled implements this.
  • Setting is a tiny but interesting feature — a pooled MySQL conn may have session vars set on it; on return, we reset them.
  • This lets vtgate pretend to be stateful (per-app SET) over a stateless pool.

vttablet's three pools, in code

  • go/vt/vttablet/tabletserver/connpool/ — the connpool package shared by all three.
  • go/vt/vttablet/tabletserver/tx_engine.go — the tx pool; transactions live as numbered resources.
  • go/vt/vttablet/tabletserver/query_engine.go — wires the read-only conn pool to the executor.
Watch for these in PRs
Flags like --queryserver-config-pool-size, --queryserver-config-transaction-cap. Misconfiguring them is the #1 cause of "vttablet is rejecting queries under load".

The transaction lifecycle

  1. App: BEGIN arrives at vtgate.
  2. vtgate: routes to a shard (or several), tells each vttablet "start txn".
  3. vttablet: leases a conn from the tx pool, runs BEGIN on it, returns a transaction_id.
  4. App: sends queries with that txn id; vttablet looks up the leased conn.
  5. App: COMMIT. vttablet runs COMMIT, returns the conn to the pool.

Look at go/vt/vttablet/tabletmanager/rpc_transaction.go for the RPC plumbing.

Pool exhaustion → timeouts → cascading failure

  • If all pool slots are leased and a new caller arrives, the pool either waits (up to a timeout) or rejects.
  • In Vitess, this surfaces as resource pool timed out errors with vterrors code RESOURCE_EXHAUSTED.
  • The lesson: long transactions = held pool slots = blocked everyone else.
Anti-pattern
Opening a Vitess transaction, then doing slow work in the app (HTTP call, etc.) before committing. That conn is locked the entire time. Don't.

dbconnpool — the older, simpler pool

  • go/vt/dbconnpool/ — older pool used by vtctld, mysqlctl, etc.
  • Wraps go/mysql/Conn in a poolable resource.
  • Simpler than vttablet's, no transaction tracking.

vttablet has moved to smartconnpool; dbconnpool remains for the control-plane bits.

Try it yourself

15-minute walk
  1. Open go/pools/resource_pool.go and find the Get method. See how it handles the wait + timeout case.
  2. Open go/pools/smartconnpool/ and skim pool.go. The optimizations are about avoiding a central mutex.
  3. Grep poolSize across go/vt/vttablet/ to see how many separate pool configs exist.

Checkpoint quiz

1. Why does a transaction hold a pool slot the entire time it's open?
Reveal
A MySQL connection is stateful inside a transaction — the BEGIN locked the conn, subsequent statements must run on the same conn, COMMIT/ROLLBACK releases it. vttablet can't reuse it in the meantime.
2. What error do you see in logs when a pool is exhausted?
Reveal
resource pool timed out with gRPC code RESOURCE_EXHAUSTED. Symptom: slow queries pile up; healthy queries fail despite mysqld looking idle.
3. What's the difference between smartconnpool and the older resource_pool?
Reveal
smartconnpool reduces lock contention and tracks connection settings (session vars) per slot. It's the modern choice; resource_pool is still used in older code paths (vtctld, mysqlctl).

Part I recap:

  • MySQL = server layer + InnoDB. Binlog is the audit log of writes.
  • GTIDs make replication topology-independent. Vitess depends on them.
  • Wire protocol is binary, length-prefixed, packet-framed.
  • Pools are everywhere; understand the layers or get bitten.
