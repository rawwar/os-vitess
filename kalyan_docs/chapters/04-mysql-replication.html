Part I · Chapter 9

Binlogs & GTIDs.

If MySQL is a tree of writes, the binlog is the audit log of that tree. Vitess reads it for breakfast.

Learning objectives

By the end of this chapter, you will
  • Draw the primary → replicas picture and label which side writes the binlog.
  • Tell apart STATEMENT, ROW, MIXED — and know why Vitess needs ROW.
  • Describe a GTID and why it makes failover much easier.
  • Find Vitess's flavor abstraction in go/mysql/flavor.go.

Replication in plain English Beginner

One MySQL is the primary. It accepts every INSERT, UPDATE, DELETE. Each change is appended to the binlog.

Other MySQLs are replicas. They open a long-running connection to the primary, stream the binlog, and replay each event locally.

Result: replicas have (almost) the same data as the primary, slightly delayed. Apps can read from them to scale read throughput.

Why Vitess loves this
Replication is also how Vitess moves data — between shards, into new shards, into shadow tables for online DDL. Same engine, different consumers.

The basic picture

flowchart LR Client[client] -->|INSERT/UPDATE| Primary[(primary mysqld)] Primary -->|binlog dump| Replica1[(replica)] Primary -->|binlog dump| Replica2[(replica)] Primary -. binlog file .- Disk[(binlog files)]
  • Primary writes every change to its binary log.
  • Replicas open a "binlog dump" connection and stream events.
  • Replicas apply events to their own copy of the data.
  • Replication is async by default; semi-sync is opt-in (replicas ack receipt before primary commits).

Binlog format: STATEMENT vs ROW vs MIXED

FormatWhat's loggedProCon
STATEMENTThe SQL stringCompactNon-deterministic queries (NOW(), UUID(), AUTO_INC races) diverge replicas
ROWBefore/after row imagesAlways replays exactlyBigger, no SQL-text grep
MIXEDSTATEMENT, falls back to ROWBest of bothSurprising switches
Vitess requires ROW
VReplication relies on row images. STATEMENT-based binlogs will not work with VReplication. See go/mysql/binlog_event_rbr.go for the row-event parser.

What a binlog event looks like (mentally)

# at 1234
#220312 10:00:01 server id 1  end_log_pos 1300
GTID 3E11FA47-71CA-11E1-9E33-C80AA9429562:7
BEGIN
# at 1300
TABLE_MAP_EVENT: db=commerce, table=customer
WRITE_ROWS_EVENT:
  INSERT INTO `commerce`.`customer` VALUES (42, 'alice@example.com')
# at 1500
XID 67890
COMMIT
  • TABLE_MAP_EVENT tells you the table schema (column types) for the upcoming row events.
  • WRITE/UPDATE/DELETE_ROWS_EVENT carries the actual row images.
  • XID marks transaction commit.

GTIDs: every transaction has a name

  • GTID = Global Transaction ID. Unique across the replication topology.
  • MySQL format: server-uuid:transaction-number, e.g. 3E11FA47-...:42.
  • MariaDB has its own GTID format: domain-server_id-sequence, e.g. 0-1-100.
  • Replicas track which GTIDs they've executed; if they reconnect, they ask for "everything after X".
Why Vitess loves GTIDs
Without GTIDs, a replica reconnecting to a new primary has to be told "start at byte 1,234,567 of binlog file mysql-bin.000042" — which only the old primary knew. With GTIDs, any replica can say "I'm at GTID X, give me the rest" to anyone.

Semi-sync vs async, and why Vitess cares

  • Async: primary commits, then writes to binlog, then notifies replicas. If primary dies, last few txns can be lost.
  • Semi-sync: primary waits for at least one replica to ack receipt of the event before returning COMMIT to the client.
  • Vitess strongly encourages semi-sync — VTOrc (chapter 18) failover depends on at least one replica having the data.
"Lossless" failovers need semi-sync
EmergencyReparentShard's correctness story assumes the most-advanced replica has the data. Without semi-sync, "most advanced replica" can still be behind the failed primary.

Common misconceptions

"Async replication still loses no data"
Async means primary doesn't wait. If the primary dies between binlog write and replica fetch, those events are gone. Use semi-sync for stronger guarantees.
"GTIDs replace binlog positions"
GTIDs are identifiers for transactions. Binlog files still exist; GTIDs just give every transaction a name that doesn't depend on which file/byte it was in. Both coexist.
"STATEMENT format is fine for replication"
For simple cases yes. But UPDATE x SET created_at = NOW() can produce different results on the replica's clock. Vitess requires ROW so VReplication can apply rows precisely.

Try it yourself Lab

10 min · any MySQL with binlogs on
  1. Make sure binlog is on: 
    SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_format';
    If binlog_format isn't ROW, the next steps still work but events will look different.
  2. Look at current state: 
    SHOW MASTER STATUS;
SHOW BINARY LOGS;
  3. Pick the most recent file from SHOW BINARY LOGS, then dump its tail: 
    SHOW BINLOG EVENTS IN 'binlog.000001' LIMIT 20;
  4. Make a tiny change: 
    CREATE TABLE IF NOT EXISTS t (id INT PRIMARY KEY);
INSERT INTO t VALUES (1);
  5. Re-run the binlog events query. Your INSERT should appear.
What to notice
  • You'll see Anonymous_Gtid or a Gtid event marking your transaction.
  • If binlog format is ROW, you'll see a Table_map event followed by a Write_rows event — not the literal SQL.
  • This is exactly the byte stream that VReplication consumes.

Checkpoint quiz

1. Why does Vitess require ROW format, not STATEMENT?
Reveal
VReplication reapplies events on a different shard or different schema. STATEMENT-based replication can produce different results when re-executed (NOW(), AUTO_INCREMENT, etc.). ROW format records the exact before/after row values — deterministic.
2. Without GTIDs, what does a replica say to reconnect to its source?
Reveal
"Start at byte X of file Y." That only makes sense to the original primary. If the primary moves, the position is meaningless. With GTIDs the replica says "I've executed up to GTID Z" — meaningful to any source.
3. Why is semi-sync important for Vitess failover correctness?
Reveal
When the primary dies, Vitess picks the most-advanced replica to promote. Semi-sync guarantees at least one replica had the data the primary acked to clients — so the "most advanced" replica really does have everything.
