Part III · Chapter 19

From AST to plan.

The planner is the most algorithmic part of Vitess. We won't read it line-by-line — that's months. We'll get the shape right and find your way around.

Learning objectives

By the end of this chapter, you will
  • Name the 5 pipeline stages: semantics → operator tree → physical plan → primitives → cache.
  • Predict, for a given WHERE clause, whether the planner picks EqualUnique, IN, or Scatter.
  • Use VEXPLAIN PLAN on your local cluster to see plans.
  • Find a testdata/*.json file under planbuilder/ and add a new case to it.

Our running example, planned

SELECT c.customer_id, c.email FROM customer c WHERE c.customer_id = 42

Because customer is sharded by customer_id with a hash vindex, and the predicate is customer_id = 42 (unique vindex match), the planner short-circuits via the "single-sharded shortcut":

Plan:
  Route {
    Opcode:   EqualUnique
    Keyspace: customer
    Vindex:   hash
    Values:   [42]
    Query:    "select c.customer_id, c.email from customer as c where c.customer_id = :vtg1"
  }

One shard touched. No join, no aggregation, no scatter. This is the fast path most OLTP traffic takes.

What the planner produces

An engine.Plan: a tree of primitives from go/vt/vtgate/engine/.

  • Route — send a query to one or more shards
  • Join, HashJoin — combine results from two children
  • Aggregate, OrderedAggregate, ScalarAggregate — group/sum/min/max
  • Limit, Filter, Projection, Distinct
  • Concatenate — UNION
  • InsertSelect, Update, Delete
  • … and ~30 more

The five-step pipeline

flowchart LR AST[AST
from sqlparser] --> Sem[semantic
analysis] Sem --> Op[Operator tree
logical plan] Op --> Phys[Physical plan
cost-based pick] Phys --> Prim[Engine primitives] Prim --> Cache[Plan cache]
  1. Semantic analysis — resolve names, scopes, types
  2. Operator tree — a logical, sharding-aware tree
  3. Physical planning — push filters down, pick joins
  4. Primitive generation — convert to engine.Plan
  5. Cache — keyed by SQL + vschema version

Semantic analysis

  • go/vt/vtgate/semantics/ — its own package.
  • SemTable: column → table mapping, type info, scope tree.
  • Catches "column X is ambiguous", "no such table", type mismatches before planning.
  • The output feeds the planner with "for this *ColName AST node, here's exactly which table column it refers to".
semTable, err := semantics.Analyze(stmt, currentDB, vschema)

Operator tree

  • go/vt/vtgate/planbuilder/operators/ — operator definitions.
  • Route, Join, Filter, Projection, Aggregator, Limit, etc.
  • Functional/algebraic-style — each operator can be rewritten by passes.
  • Rules apply: predicate pushdown, constant folding, dedup, cross-keyspace boundary checks.

The operator tree is where the cleverness lives.

Physical planning

  • Decide: which join algorithm? scatter or single-route? do we need an aggregator on vtgate or push it to the shard?
  • Lower-cost wins. Cost = approximate: scatter > single-shard, MemoryTable > Sort, etc.
  • The "Gen4" planner is the current generation (Gen3, the older one, was retired in v17/18).

See go/vt/vtgate/planbuilder/operator_transformers.go — operator → engine primitive.

The "single-sharded shortcut"

  • If the planner can prove the query touches a single shard, it short-circuits — emits one Route and skips most analysis.
  • go/vt/vtgate/planbuilder/single_sharded_shortcut.go
  • Huge perf win for routine OLTP — most queries hit just one shard.

The plan cache

  • Plans are expensive to build; identical SQL is cheap to re-run.
  • Cache key: normalized SQL + vschema version + a few session bits.
  • LRU bounded by size (memory accounting via the generated cached_size.go files).
  • go/cache/theine/ — TheineW cache impl.
  • Expose at /debug/query_plans on vtgate.

Plan tests: the gift that keeps giving

  • go/vt/vtgate/planbuilder/testdata/ — hundreds of JSON files.
  • Each pair: SQL in, expected plan out.
  • To debug a planner bug: add the failing SQL, run plan_test.go, see the diff.
  • Best place to learn what the planner is supposed to produce.
Open one
ls go/vt/vtgate/planbuilder/testdata/ | head -20 — try select_cases.json. Each entry shows you the AST → plan mapping in plain text.

vexplain: see plans live

VEXPLAIN PLAN SELECT * FROM customer WHERE id = 42;
VEXPLAIN QUERIES SELECT * FROM customer WHERE id = 42;
VEXPLAIN ALL SELECT * FROM customer WHERE id = 42;
  • PLAN — the high-level plan tree
  • QUERIES — what gets sent to each tablet
  • ALL — both, plus execution stats

Run from any MySQL client connected to vtgate. Indispensable.

Cross-keyspace queries

  • Joining tables from two different keyspaces? You need the planner to know about both vschemas.
  • vtgate config flag NoCrossKeyspaceJoins (zero-value preserves old behavior — see CLAUDE.md note on negative-polarity bools).
  • The operator-tree pass checks if a join can cross keyspaces.

Checkpoint quiz

1. SELECT * FROM customer WHERE email = 'a@x.com' on a keyspace sharded by customer_id: what does the planner produce?
Reveal
Without a secondary lookup vindex on email, this is a Scatter — vtgate sends the query to every shard, dedupes results. With a lookup vindex on email, it becomes an EqualUnique route to one shard.
2. Why does SELECT AVG(x) across shards need a special trick?
Reveal
You can't average partial averages directly. The planner asks each shard for SUM(x) and COUNT(x), then divides at vtgate. SUM and COUNT compose; AVG doesn't.
3. Why is the plan cache keyed on normalized SQL + vschema version?
Reveal
Normalized SQL means literals (42, 99) became bind vars, so all "where id = N" queries share one plan. vschema version means: if sharding rules change, old plans are invalidated automatically.
