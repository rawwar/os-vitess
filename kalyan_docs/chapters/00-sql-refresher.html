The SQL you need.

A focused refresher on the SQL you'll see throughout this course. We'll use a tiny e-commerce schema that you'll meet again in chapters 4, 14, 22, and 25 — so it's worth memorizing the table names.

What this chapter gives you

  • Know what INSERT, UPDATE, DELETE do and what could go wrong.
  • Explain what an index is — and why more indexes can be a bad thing.
  • Use a transaction correctly and know what Vitess changes about it.

This isn't a complete SQL textbook. It's the subset of SQL you actually need to follow every other chapter in this course. If you're already fluent in SQL, skim this chapter — you'll still want to read the "What Vitess changes about transactions" section.

Our sample schema

Throughout this course we'll use the same e-commerce schema: four small tables representing customers, products, orders, and order lines. The Vitess local example (chapter 14) uses the same schema, so what you learn here will translate directly when we run real queries through vtgate later.

CREATE TABLE customer (
  customer_id  INT PRIMARY KEY,
  email        VARCHAR(128) NOT NULL,
  country      VARCHAR(2)   NOT NULL
);

CREATE TABLE product (
  product_id   INT PRIMARY KEY,
  name         VARCHAR(64),
  price_cents  INT NOT NULL
);

CREATE TABLE corder (
  order_id     INT PRIMARY KEY,
  customer_id  INT NOT NULL,
  created_at   DATETIME NOT NULL
);

CREATE TABLE order_line (
  order_id     INT NOT NULL,
  product_id   INT NOT NULL,
  quantity     INT NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

Two things to notice. First, order_line has a composite primary key — the combination of order_id and product_id is unique, not either column alone. This pattern shows up constantly in real schemas. Second, the orders table is called corder, not order. ORDER is a SQL reserved word (think ORDER BY); many setups won't let you name a table that way without painful quoting. Vitess's local demo uses the same workaround. Make peace with the name now.

SELECT: fetching rows

A SELECT statement reads rows from one or more tables. The clauses run in a specific order even though you write them in another. Read SQL roughly right-to-left in your head: FROM picks the table, WHERE filters rows, SELECT picks which columns to return, ORDER BY sorts, and LIMIT trims. The English-style ordering of clauses is convenient to write but doesn't reflect execution order.

-- Get one customer
SELECT customer_id, email
FROM customer
WHERE customer_id = 1;

-- Filter by another column
SELECT email FROM customer WHERE country = 'US';

-- Sort and limit
SELECT customer_id, email
FROM customer
ORDER BY email
LIMIT 10;

The first query returns a single row (because customer_id is the primary key, unique by definition). The second returns all US customers. The third sorts by email and returns the first ten — useful for paging through a long list.

Why this matters for Vitess
When you run that first query through vtgate against a sharded keyspace, vtgate uses customer_id = 1 to figure out which exact shard owns that row, and sends the query only there. The second query, without a vindex predicate, becomes a scatter — sent to every shard and combined. The third's sort behaves differently across shards (each shard sorts its slice; vtgate merges). All of this is the planner's job, but it's grounded in plain SQL like this.

JOIN: combining tables

Real queries rarely touch just one table. A JOIN stitches rows from two tables together based on a matching condition.

-- Each customer paired with their orders
SELECT c.customer_id, c.email, o.order_id, o.created_at
FROM customer c
JOIN corder o ON o.customer_id = c.customer_id
WHERE c.customer_id = 1;

That's an INNER JOIN (the default when you just write JOIN). It returns only rows where both sides match — customers with at least one order. Customers who have never ordered won't appear.

A LEFT JOIN keeps every row from the left-side table even if the right side has nothing to match. Columns from the right side become NULL for those rows, which is exactly how you find "customers who have never ordered":

SELECT c.customer_id, c.email
FROM customer c
LEFT JOIN corder o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

The IS NULL at the end is the trick — for customers with no orders, the right-side columns are NULL, so o.order_id IS NULL matches them.

Worked example: a four-way join

To make this concrete, here's a real question: how much has each customer spent in total? We need to join four tables — customer to order to order_line to product — and aggregate the totals.

SELECT c.customer_id,
       SUM(ol.quantity * p.price_cents) AS spend_cents
FROM customer c
JOIN corder o      ON o.customer_id = c.customer_id
JOIN order_line ol ON ol.order_id   = o.order_id
JOIN product p     ON p.product_id  = ol.product_id
GROUP BY c.customer_id
ORDER BY spend_cents DESC;

Walk it slowly. FROM customer c starts with every customer. The first JOIN pairs each customer with their orders. The second joins each order to its line items. The third joins each line item to the product (for the price). At that point each row in the joined result contains: a customer, an order, a line, and that line's product — including quantity and price_cents. We compute quantity * price_cents for each row, group by customer, and sum the per-row spend.

This is a perfectly normal query against a single MySQL. Through Vitess, on a keyspace sharded by customer_id, it still works — but the planner has to send it to every shard, aggregate per-shard, and combine the results at vtgate. Chapter 19 (the planner) and chapter 20 (the engine) trace exactly how.

Reveal the answer

Bob has no orders, but the LEFT JOIN keeps his row anyway. COUNT(o.order_id) counts non-null order IDs, so Bob gets 0, not 1 (and not NULL). If you wrote COUNT(*) instead, Bob would have 1 — because COUNT(*) counts the row regardless of nulls. This kind of distinction is exactly why NULL is the most-debated feature in SQL.

GROUP BY and aggregates

An aggregate collapses many rows into one. COUNT, SUM, MIN, MAX, and AVG are the five you'll see most.

GROUP BY partitions the rows by some column(s), then applies the aggregate to each group. The result has one row per group:

-- Number of orders per customer
SELECT customer_id, COUNT(*) AS n_orders
FROM corder
GROUP BY customer_id;

-- Total revenue per product, top first
SELECT ol.product_id, SUM(ol.quantity * p.price_cents) AS revenue
FROM order_line ol
JOIN product p ON p.product_id = ol.product_id
GROUP BY ol.product_id
ORDER BY revenue DESC;

The rule of thumb: in a query with GROUP BY, every column in the SELECT list must either appear in the GROUP BY or be wrapped in an aggregate function. (Some MySQL configurations relax this, with surprising results. Don't rely on that.)

Aggregates across shards
Aggregates that "compose" — SUM, COUNT, MIN, MAX — are easy for Vitess to scatter: each shard returns its partial result, vtgate combines them. AVG is trickier: averaging averages is wrong. So Vitess asks each shard for SUM and COUNT separately and divides at the end. This kind of detail lives in go/vt/vtgate/engine/aggregations.go; we'll read it in chapter 20.

INSERT, UPDATE, DELETE

The three statements that actually change data are forgivingly simple:

INSERT INTO customer (customer_id, email, country)
VALUES (4, 'dave@example.com', 'US');

UPDATE customer
SET country = 'UK'
WHERE customer_id = 4;

DELETE FROM customer WHERE customer_id = 4;

And forgivingly dangerous. An UPDATE without a WHERE updates every row in the table. Same for DELETE. There is no undo (outside of restoring from a backup, which usually means hours of downtime).

The unfiltered UPDATE / DELETE
Before running a destructive statement, get into the habit of running the equivalent SELECT first to see exactly which rows you're about to change.

Step 1: SELECT * FROM customer WHERE country = 'XX';
Step 2: look at the result.
Step 3: only then, UPDATE customer SET ... WHERE country = 'XX';

Many production query rules (including Vitess's --queryserver-config-strict-table-acl and the vttablet rules engine) exist specifically to prevent these mistakes.

What is an index, really?

Rows live on disk in pages (chapter 3 makes this concrete). To find customer_id = 42 without an index, the database has to scan every row in the table, comparing each — that's O(N) work. An index is a separate, sorted lookup structure that lets the database jump straight to the row in O(log N) time.

1Without an index: scan every row.
flowchart LR q[query: id=42] --> r1[row 1] r1 --> r2[row 2] r2 --> r3[row 3] r3 --> rmore[...] rmore --> rN[row N]
2With an index: tree lookup, ~4-5 hops for a billion rows.
flowchart TB root["[50]"] --> a["[20]"] root --> b["[80]"] a --> a1["rows 1-19"] a --> a2["rows 20-49"] b --> b1["rows 50-79"] b --> b2["rows 80-N"]

Indexes have a real cost. They consume disk space (a few percent of the table size, usually). More importantly, every INSERT, UPDATE, or DELETE on the table has to update every index that mentions the affected columns. More indexes mean faster reads on the indexed columns and slower writes on the whole table. There's no free lunch.

Common misconceptions about indexes

"An index is just a copy of the table"
It's a separate sorted structure, but it usually stores only the indexed columns plus a pointer to the row (in InnoDB, that pointer is the primary key, not a physical address). It's smaller than the table — sometimes much smaller.
"More indexes = faster"
Faster reads on the indexed columns. Slower writes on the whole table. The database has to maintain every index on every relevant change. Most production tables sit at 3-7 indexes total; more than that should be justified by query-pattern data.
"WHERE email LIKE '%@gmail.com' will use the email index"
No. B-tree indexes work left-to-right — the database can find a prefix, but can't seek by a suffix. A leading % wildcard defeats the index and forces a full scan. WHERE email LIKE 'alice%' does use the index.

Transactions: all or nothing

A transaction is a group of statements that succeed or fail as a unit. Either every statement takes effect (COMMIT) or none do (ROLLBACK).

BEGIN;
  INSERT INTO corder (order_id, customer_id, created_at)
    VALUES (104, 1, NOW());
  INSERT INTO order_line (order_id, product_id, quantity)
    VALUES (104, 7, 2);
COMMIT;

If the second INSERT fails (maybe product 7 doesn't exist, and there's a foreign key constraint), the first one is also rolled back. The database moves from one consistent state to another without ever exposing the in-between.

The three commands:

  • BEGIN (or START TRANSACTION) — open a transaction.
  • COMMIT — finalize all changes since BEGIN.
  • ROLLBACK — discard all changes since BEGIN.

Transactions are the foundation of every reliable application. The reason your bank balance doesn't randomly disappear is, in part, that the transfer-money operation is wrapped in a transaction. Vitess preserves these guarantees within a single shard with no asterisk.

What Vitess changes about transactions

In plain MySQL, a transaction lives on one server. In Vitess, a transaction could touch multiple shards — multiple MySQLs running on different machines. That changes the rules in a way you have to internalize before reading any Vitess code.

Single-shard transaction

Full MySQL guarantees apply. BEGIN, statements, COMMIT behave exactly as you'd expect on plain MySQL.

This is the case for any query whose WHERE clause includes the shard key with an equality predicate.

Cross-shard transaction

Each shard's piece commits independently. If shard 2 fails after shard 1 already committed, you have a partial commit — unless you've opted into two-phase commit (2PC), which adds latency and complexity.

Most apps avoid this by designing the schema so related rows live on the same shard.

This is one of the deepest design constraints in Vitess. We'll see how it's implemented in chapter 17 (vtgate's transaction handling) and chapter 22 (vttablet's transaction engine).

NULL traps

NULL is SQL's way of saying "unknown". It is not zero, it is not the empty string, and it is not false. Critically, NULL = NULL is not true — it's NULL, because "is unknown equal to unknown?" is itself unknown.

This trips up everyone. A few traps:

-- This finds ZERO rows, even if hundreds have NULL country:
SELECT * FROM customer WHERE country = NULL;

-- This is the correct way to look for nulls:
SELECT * FROM customer WHERE country IS NULL;

-- COUNT(col) ignores NULLs:
SELECT COUNT(country) FROM customer;
-- This returns the number of NON-NULL country values.

-- COUNT(*) counts every row, NULL or not:
SELECT COUNT(*) FROM customer;

-- Arithmetic propagates NULL:
SELECT 1 + NULL;  -- returns NULL, not 1.

Anytime a column is nullable, you have to think about what your query does with the nulls. The shortest debugging session of your life will end when you realize WHERE col != 'x' excluded all the rows where col is NULL — because NULL != 'x' is NULL, not true.

Checkpoint quiz

1. What does LEFT JOIN guarantee that INNER JOIN doesn't?
Reveal
Every row from the left-side table appears in the result, even if no matching row exists on the right. Right-side columns will be NULL for those rows.
2. WHERE country = NULL on a 1000-row table where 50 rows have NULL country returns how many rows?
Reveal
Zero. = NULL is never true; the result is always NULL, which doesn't match. You need IS NULL.
3. You added five new indexes to speed up a slow report. The report is now fast, but INSERT latency tripled. Why?
Reveal
Every INSERT now updates five additional index structures. Reads were the bottleneck; you traded write throughput to fix it. Often the right call — but it should be a conscious trade-off, not an accident.
4. Inside a single MySQL, a transaction guarantees atomicity. What's different when that transaction touches two Vitess shards by default?
Reveal
Each shard's piece commits independently. If the second shard fails after the first committed, you have a partial commit. Vitess offers two-phase commit (2PC) as an opt-in to fix this, with a latency cost. Most apps avoid the situation by keeping related rows on the same shard.
5. In our schema, why is the orders table called corder instead of order?
Reveal
ORDER is a SQL reserved word (as in ORDER BY). Naming a table with a reserved word requires quoting it everywhere, which gets old fast. corder ("customer order") sidesteps the issue. The Vitess local demo uses the same trick.
