Speaking MySQL.

vtgate has to pretend to be MySQL, and vttablet has to talk to MySQL. Both halves live in go/mysql/.

Learning objectives

By the end of this chapter, you will
  • Explain what a wire protocol is using fewer than three sentences.
  • Recognize the 4-byte MySQL packet header in a hex dump.
  • Find go/mysql/conn.go and identify the Conn struct.
  • Locate where vtgate's server role is implemented (plugin_mysql_server.go).

What is the "wire protocol"?

  • A binary, length-prefixed packet format over TCP (port 3306) or a Unix socket.
  • Stateful: handshake → auth → query/response loop → close.
  • Documented at dev.mysql.com — but you almost never need to read the official doc once you've read Vitess's implementation.

Vitess implements both sides: a server (listener) for vtgate, and a client (Conn) for talking to mysqld.

The packet, in one slide

+----------+----------+----------+----------+--- ... ---+
|  length  |  length  |  length  | sequence |  payload  |
|  byte 0  |  byte 1  |  byte 2  |   id     |  N bytes  |
+----------+----------+----------+----------+--- ... ---+
        24-bit little-endian            1 byte    up to (2^24 - 1)
  • Header = 4 bytes: 3 for length, 1 for sequence number.
  • Sequence wraps at 256, reset every command.
  • Payloads > 16 MB split into multiple packets.
go/mysql/conn.go — const PacketHeaderSize = 4

The Conn struct (the heart of go/mysql/)

// Conn is a connection between a client and a server, using the MySQL
// binary protocol. It is built on top of an existing net.Conn, that
// has already been established.
//
// Use Connect on the client side to create a connection.
// Use NewListener to create a server side and listen for connections.
type Conn struct {
    fields []*querypb.Field
    salt   []byte
    authPluginName AuthMethodDescription
    schemaName string
    // ... bufio reader/writer, ephemeral buffers, mutex, etc.
}
go/mysql/conn.go:75
  • Same struct, both sides. Client and server share buffering, packet framing, charset handling.
  • Ephemeral buffer reuse — see the ephemeralRead / ephemeralWrite state to avoid allocations on every packet.

Server side: Listener

  • go/mysql/server.go — NewListener(), Listener.Accept(), dispatches each connection to a Handler.

The query loop, in pseudocode

// server side, simplified
for {
    pkt, err := c.readEphemeralPacket()
    if err != nil { return }
    switch pkt[0] {
    case ComQuery:
        // 1-byte command, rest is SQL
        sql := string(pkt[1:])
        handler.ComQuery(c, sql, func(qr *sqltypes.Result) error {
            return c.writeResult(qr)
        })
    case ComStmtPrepare:  // ...
    case ComStmtExecute:  // ...
    case ComPing:         // ...
    case ComQuit:         return
    }
}

That's it. Everything else is variations: result encoding, prepared statements, COM_BINLOG_DUMP, etc.

Result encoding (server → client)

  1. Column count packet (LengthEncoded int).
  2. N column-definition packets (name, type, flags).
  3. EOF or OK (depending on capability flags).
  4. 0+ row packets (one row per packet).
  5. EOF.
go/mysql/query.go — see writeFields, writeRow, writeEndResult

Vitess uses sqltypes.Result internally and converts at the boundary.

Flavor: handling MySQL vs MariaDB vs Percona

  • Different servers, mostly the same protocol — but binlog events, GTID format, and a few sysvars differ.
  • go/mysql/flavor.go — the flavor interface; one impl per vendor.
  • go/mysql/flavor_mysql.go, flavor_mariadb.go, flavor_percona.go.
House rule (from CLAUDE.md)
Version-specific behavior belongs in the flavor file, not in generic code. If you find yourself writing if isMariaDB in conn.go, stop — add it to the flavor instead.

Checkpoint quiz

1. Vitess implements both sides of the MySQL protocol. Why both?
Reveal
vtgate speaks MySQL to apps (as a server). vttablet (and vtgate's internal client) talks MySQL to mysqld (as a client). The protocol code is symmetric, so the same Conn struct serves both roles.
2. What does the Handler interface in go/mysql/server.go let you do?
Reveal
Plug different "what to do when a SQL packet arrives" handlers into the same MySQL listener. vtgate plugs in a handler that routes the query into its planner+executor. Tests plug in a fake.
3. Why does flavor logic live in flavor_mysql.go / flavor_mariadb.go rather than in conn.go?
Reveal
CLAUDE.md rule: MySQL-version-specific behavior belongs in the flavor implementation, not generic code. Otherwise conn.go would be a swamp of if isMariaDB branches.
