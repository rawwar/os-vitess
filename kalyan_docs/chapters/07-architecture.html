The five processes.

A minimal Vitess cluster has five kinds of process. Once you know what each does, the rest of the codebase organizes itself.

Learning objectives

By the end of this chapter, you will
  • Name every process in a minimal cluster and its one-line job.
  • Trace a query from app to mysqld in 4 hops.
  • Locate the matching go/cmd/<binary>/ and go/vt/<subsystem>/ dirs.
  • Use analogies (router / sidecar / filing cabinet) when explaining to a non-Vitess person.

vtgate

  • What it is: a stateless TCP proxy that looks like MySQL.
  • What it does: auth, parse SQL, look up vschema, plan, route, scatter-gather, return results.
  • How you scale it: horizontally. Run as many vtgates as you need; round-robin them with a load balancer.
  • Where it lives: go/cmd/vtgate/ (entrypoint), go/vt/vtgate/ (logic).
Mental model
vtgate is the database from the app's point of view. Everything that "feels like MySQL but smarter" — that's vtgate.

vttablet

  • What it is: a sidecar process colocated with each mysqld.
  • What it does: connection pooling, query rewriting (consistent across pools), schema tracking, txn lifecycle, replication tracking, throttling, online DDL.
  • One per mysqld. If you have 100 shards × 3 replicas = 300 vttablets.
  • Where it lives: go/cmd/vttablet/ + go/vt/vttablet/.
Mental model
vttablet is "MySQL, but with safety belts". It refuses to do stupid things, retries smart things, and translates between Vitess's RPC world and MySQL's wire world.

vtctld & vtctldclient

  • vtctld: the control plane. Long-running daemon that operators talk to.
  • vtctldclient: the CLI you actually use day-to-day. RPCs to vtctld.
  • Used for: creating keyspaces, initializing shards, MoveTables, Reshard, OnlineDDL, backups, vdiff.
  • go/cmd/vtctld/, go/cmd/vtctldclient/, go/vt/vtctld/.

There's also a legacy vtctl binary; new commands go through vtctldclient.

vtorc

  • What it is: Vitess's fork of Orchestrator (born in MySQL ops land).
  • What it does: watches replication topology; promotes a new primary when one fails.
  • Where it lives: go/cmd/vtorc/ + go/vt/vtorc/.
  • Talks to: mysqld directly (for probing), topo (for cluster state), vtctld (to trigger PRS/ERS).
ERS = Emergency Reparent Shard
When the primary is dead, vtorc triggers ERS — a careful protocol that promotes the most advanced replica. CLAUDE.md has strict rules about touching this code. We cover it in chapter 18.

The topology service

  • What it is: a tiny configuration store with a strong consistency guarantee.
  • What lives there: list of cells, keyspaces, shards, tablet records, vschema, routing rules, online DDL state.
  • Implementations: etcd, ZooKeeper, consul. In-memory for tests.
  • go/vt/topo/ is the abstraction; subdirs are impls.
Mental model
topo is "the filing cabinet". Vitess's processes coordinate by reading and writing files in this filing cabinet. Chapter 11 walks the code.

How they cooperate: a query in flight

sequenceDiagram participant App participant vtgate participant topo participant vttablet participant mysqld App->>vtgate: SELECT * FROM customer WHERE id = 42 vtgate->>topo: GetSrvKeyspace("commerce") (cached) vtgate->>vtgate: parse + plan: routes to shard "-80" vtgate->>vttablet: ExecuteQuery (gRPC) vttablet->>vttablet: rewrite, lease pool conn vttablet->>mysqld: SELECT ... mysqld-->>vttablet: rows vttablet-->>vtgate: rows vtgate-->>App: rows

And during a failover

sequenceDiagram participant vtorc participant topo participant vtctld participant tabletA as primary tablet (dies) participant tabletB as replica tablet tabletA--xvtorc: probe fails vtorc->>vtorc: confirm dead via topo / other tablets vtorc->>vtctld: EmergencyReparentShard vtctld->>topo: take shard lock vtctld->>tabletB: find most-advanced replica vtctld->>tabletB: promote to primary vtctld->>topo: update shard record vtctld->>topo: release lock

Cells: the unit of "datacenter"

  • A cell is one failure domain (usually one DC or one AZ).
  • Topo has a global cell + one per regional cell.
  • vtgate prefers tablets in its own cell; will failover across cells when needed.

You'll see the term constantly: cell, SrvKeyspace (per-cell view), --cells_to_watch, etc.

Try it yourself

10-min map
  1. ls go/cmd/ — count the binaries Vitess produces.
  2. ls go/vt/ — see the matching impl packages.
  3. Find the entrypoint of vtgate: go/cmd/vtgate/vtgate.go. It's tiny — most of it just delegates to cli/.

Checkpoint quiz

1. Which process is stateless?
Reveal
vtgate. It holds no persistent state — everything it knows comes from topo or healthchecks. That's what lets you scale vtgates horizontally and replace them freely.
2. Why is there one vttablet per mysqld and not, say, one per shard?
Reveal
vttablet manages a specific mysqld process — connection pools, replication settings, schema reload. A shard has multiple mysqlds (primary + replicas), each with its own vttablet sidecar.
3. The primary dies. Who notices first? Who decides what to do?
Reveal
vtorc notices (it's probing). It calls vtctld with "EmergencyReparentShard". vtctld coordinates: stop replication on all replicas, find the most-advanced one, promote it, point everyone else at the new primary.
