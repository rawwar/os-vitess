Part IV · Chapter 21

The MySQL sidecar.

vttablet runs alongside every mysqld. It's the safety belt, the connection multiplexer, the schema oracle. Two big sub-packages: tabletserver (queries) and tabletmanager (control).

Learning objectives

By the end of this chapter, you will
  • Tell apart tabletserver (data plane) and tabletmanager (control plane).
  • Name the tablet types (PRIMARY, REPLICA, RDONLY, SPARE, DRAINED).
  • Point to the three pools and the schema engine.
  • Open a vttablet's /debug/status on your local cluster.

Why vttablet exists

  • vtgate must not connect to mysqld directly — too many connections, too much logic at the wrong layer.
  • vttablet adds: pooling, query rewriting, schema watching, throttling, replication tracking, hot row protection.
  • It also serves the "tablet manager" RPCs vtctld/vtorc use to do cluster ops.
Mental model
Think of vttablet as "MySQL's bodyguard". It refuses bad queries, retries reasonable ones, and tells vtgate exactly which queries this mysqld is healthy enough to serve.

Tablet types

  • PRIMARY — the writable replica for a shard.
  • REPLICA — read-only replicas, ready to be promoted.
  • RDONLY — read-only replicas, not for promotion. Used for OLAP-y queries, backups, VReplication sources.
  • SPARE — not serving.
  • DRAINED — also not serving.

Tablet type is stored in the topo and changed by RPC. vtgate filters discovery by tablet type when picking targets.

tabletserver: the query path

  • go/vt/vttablet/tabletserver/tabletserver.go — top-level wiring.
  • Implements go/vt/vttablet/queryservice/ · QueryService.
  • Sub-engines:
    • query_engine.go — plans + executes queries against mysqld
    • tx_engine.go — transaction lifecycle
    • schema/ — schema tracking
    • heartbeat/ — primary writes heartbeats; replicas measure lag
    • throttle/ — throttling for online DDL, VReplication

vttablet's own planner

  • Surprise: vttablet has its own mini-planner.
  • go/vt/vttablet/tabletserver/planbuilder/
  • It doesn't shard — vtgate did that. vttablet's planner rewrites for safety:
    • Add LIMIT caps
    • Detect "passthrough DML" vs. "needs subquery rewrite"
    • Recognize types (DDL, DML, SELECT, set) for routing to the right pool

The connection pools (recap)

  • Conn pool — for read-only queries.
  • Tx pool — for transactions (numbered, by txid).
  • Appserver pool — for DBA / heartbeat / control queries.
  • Sizes controlled by flags; tunable per environment.
go/vt/vttablet/tabletserver/connpool/

The schema engine

  • go/vt/vttablet/tabletserver/schema/engine.go
  • Reads information_schema at startup, caches table definitions in memory.
  • Subscribes to its own change events; refreshes after DDL.
  • Used by query planner ("does this table have column X?") and online DDL.

Health streamer

  • go/vt/vttablet/tabletserver/health_streamer.go
  • Streams real-time health updates to vtgate's discovery.
  • Carries: tablet type, replication lag, serving state, last seen GTID position.
  • If this stream goes silent, vtgate marks the tablet "unhealthy" and stops routing to it.

State manager

  • go/vt/vttablet/tabletserver/state_manager.go
  • Owns the tablet's "what type am I + am I serving" state machine.
  • Coordinated transitions:
    • PRIMARY → REPLICA (demotion during reparent) — drain transactions, stop accepting writes
    • REPLICA → PRIMARY (promotion) — wait for replication caught up, enable writes

Query rule engine

  • go/vt/vttablet/tabletserver/rules/
  • Operators can install rules: "block queries matching pattern X", "rate-limit pattern Y".
  • Push-button incident response — kill all queries from a runaway service.
  • Configured via vtctldclient; persisted in topo or memory.

Where vttablet's RPCs live

  • QueryService (vtgate ↔ vttablet):
    • go/vt/vttablet/queryservice/ — interface
    • go/vt/vttablet/grpcqueryservice/ — gRPC server impl
    • go/vt/vttablet/grpctabletconn/ — gRPC client
  • TabletManager (vtctld/vtorc ↔ vttablet):
    • go/vt/vttablet/tabletmanager/rpc_*.go — implementations
    • go/vt/vttablet/grpctmclient/ + grpctmserver/

Try it yourself

20-min walk
  1. From your local cluster: curl http://<vttablet-host>:<port>/debug/status
  2. The page lists: tablet type, serving state, pools, schemas. This is the vttablet "console".
  3. Open go/vt/vttablet/tabletserver/tabletserver.go top. Note the explicit lifecycle: Start(), StartService(), Stop().
  4. Read query_engine.go · NewQueryEngine — see how the pools are wired up.

Checkpoint quiz

1. PRIMARY vs REPLICA vs RDONLY — what's the operational difference between REPLICA and RDONLY?
Reveal
Both are read-only and follow the primary. REPLICA is eligible for promotion in a failover. RDONLY is not — it's reserved for OLAP queries, VReplication sources, and backups, so failover candidates aren't disturbed.
2. vttablet runs its own mini-planner. What does it do that vtgate's planner doesn't?
Reveal
It rewrites queries for safety (add LIMIT caps, recognize DDL vs DML), and routes the query to the right pool. No sharding logic — vtgate already decided that.
3. The health streamer goes silent. What happens?
Reveal
vtgate's discovery marks this tablet "unhealthy" and stops routing to it. Other tablets pick up the load. If enough go silent simultaneously, vtgate runs out of healthy candidates.
