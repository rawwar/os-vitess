Part VI · Chapter 32

Ship something.

You've read 31 chapters. Now turn that into a PR. This chapter is the checklist I wish I'd had.

Learning objectives

By the end of this chapter, you will
  • Pick a sensible first issue to work on.
  • Walk the local development loop (edit → test → commit → push → PR).
  • Write a PR description Vitess maintainers will actually read.
  • Read CI failures and tell flake from real failure.

Pick a first PR

  • Good first issue label on GitHub.
  • Docs typos — but note: account-age rule. New accounts (<365 days) can't submit pure spelling/grammar PRs (see CONTRIBUTING.md).
  • Flaky tests — often have a small root cause and high impact.
  • Small flag additions — gives you a tour of flag → config → behavior plumbing.

Don't start with planner internals. Start with something you can finish in a day.

Discuss first (sometimes)

  • Tiny fix: just open a PR.
  • Anything design-shaped: open an issue first, propose the approach, get a nod.
  • Touches public API or RPC schema: definitely an issue first.
  • The Vitess Slack #dev channel is the fastest path to "is this worth doing?".

The git workflow

git checkout -b fix-typo-tablet-alias
# ... make changes ...
gofumpt -w <files>
goimports -local "vitess.io/vitess" -w <files>
go test ./go/...path-of-changes/...
git add <explicit paths>        # NOT git add -A
git commit --signoff -m "fix: tablet alias formatting in error msg"
git push origin fix-typo-tablet-alias
# Open PR on github.com/vitessio/vitess
DCO sign-off is required
Every commit must have Signed-off-by: Name <email>. The --signoff flag adds it; without it, the DCO bot blocks merge.

What the bots check

  • DCO — every commit signed off.
  • cla-bot — CNCF CLA (auto-confirmed via DCO for individual contributors).
  • gofmt / gofumpt / goimports — formatting.
  • golangci-lint — many checks.
  • Unit tests — must pass.
  • e2e matrix — many suites; often the long pole.
  • codecov — coverage delta reported, not enforced.

Commit message style

vtgate: fix off-by-one in shard range calculation

When a vindex returned a keyspace ID exactly at the shard
boundary, the planner was sending the row to the wrong shard.

Add the boundary value to the lower-shard's range, matching
documentation in proto/topodata.proto.

Signed-off-by: Your Name <you@example.com>
  • Subject: imperative ("fix", "add", "update"), package prefix, ≤ 72 chars.
  • Blank line, then explain why. The diff already shows what.
  • Reference issues if any: Fixes #12345.

PR title & description

  • Title: same shape as commit subject; reviewers triage from this.
  • Description sections (template auto-fills):
    • What is changing & why?
    • Related issues
    • Tests added
    • Documentation
    • Migration notes / impact

Release notes

  • If your PR is user-visible (new flag, behavior change, bug fix), add a release-note entry.
  • Lives in changelog/<version>/<release>/summary.md
  • Keep it user-focused. Internal refactors don't need entries.
  • CLAUDE.md: "Changelog summaries are for key changes all users should know about — internal implementation details don't belong there."

Review feedback: receiving it well

  • Reviewers will be direct. Don't take it personally.
  • Address every comment — either fix or reply with reasoning.
  • Push new commits, don't amend (per CLAUDE.md, after the PR exists).
  • Mark conversations resolved when addressed; let the reviewer re-open if needed.
  • It's normal for a first PR to take 3-4 iterations.

Common gotchas (real ones)

Editing generated files
Open a "Code generated ... DO NOT EDIT" file by mistake? Discard the edit, find the source, re-generate.
Wrong flag style
New flag with an underscore (--my_flag) will fail review. Use hyphens.
Bare errors
fmt.Errorf("...") instead of vterrors.Errorf(...). Reviewers will catch this — better to learn the patterns now.
Adding unrelated diffs
Touching go.sum, package-lock.json, or formatting changes to files you didn't otherwise edit. Keep PRs focused.

If CI fails

  1. Read the failing log — usually obvious.
  2. Reproduce locally: go test ./path/... or the exact e2e suite name.
  3. If it's a known flake (search GitHub Issues for the test name), comment on the PR; a maintainer can re-run.
  4. Fix & push. New commit; don't amend.

After merge

  • Your change ships in the next minor release (typically every ~3 months).
  • Major bugs may get backported to active LTS branches by maintainers (see .claude/skills/resolve-backport/).
  • You're now in git log forever. Congrats.

Where to go from here

  • Subscribe to the Vitess Slack #dev and #release.
  • Watch the repo on GitHub — see how big PRs get reviewed.
  • Pick a subsystem; become its expert. The maintainers love when contributors specialize.
  • Attend a monthly Vitess community meeting (calendar on vitess.io/community).

Closing thoughts

Vitess is a 15-year-old codebase running at planet scale. It rewards careful reading, asking good questions, and shipping small changes that fit the existing style.

The best way to learn this codebase is to change it. Pick something, ship it, iterate.

Good luck!

First-contribution simulator Lab · 45 min

Practice the full loop without pushing
  1. Find a tiny existing test. 
    rg "func Test" go/vt/sqlparser/parse_test.go | head -5
    Pick one (e.g., TestKeywords).
  2. Read it. Understand what it asserts. 
    less go/vt/sqlparser/parse_test.go
    Find the test function by name.
  3. Make a harmless local-only change. Edit a string literal in a test case. Save.
  4. Run the test. It should fail because you changed the expectation. 
    go test -run TestKeywords ./go/vt/sqlparser/ -v
    Read the error output — get used to its shape.
  5. Inspect the diff. 
    git diff go/vt/sqlparser/parse_test.go
  6. Revert it. 
    git checkout -- go/vt/sqlparser/parse_test.go
    Confirm: git status shows no changes.
  7. Re-run the test. Passes again.
What you just simulated
The full local development loop — minus the push. When you do this for real, the only extra steps are git commit --signoff and git push.

CI failure: flake vs real Triage

Looks likeProbablyWhat to do
Same test, same line, always fails on your branchReal failureReproduce locally, fix.
"context deadline exceeded" mid-testFlake on a slow runnerComment "re-run CI" — a maintainer will trigger a retry.
Lint complains about a file you didn't touchPre-existing on mainRebase onto latest main; if persists, mention in PR.
Test fails referencing port 3306 / etcdResource conflict on runnerAlmost always a flake. Re-run.
Search before re-running
Search GitHub Issues for the failing test name. If a "flaky test" issue exists, you've confirmed it's not your fault. Link it in your PR.

Checkpoint quiz

1. You forgot the DCO sign-off on your commit. What happens, and how do you fix?
Reveal
DCO bot blocks merge. Easiest fix: add a new commit with sign-off (--allow-empty -s -m "DCO sign-off") and push. Or, only if your PR is fresh, amend the previous commit with --signoff and force-push (acceptable on a brand-new PR; never after review starts).
2. After a reviewer asks for changes, do you amend or add new commits?
Reveal
Add new commits. CLAUDE.md is explicit: never amend or force-push after a PR is open. Keeps history reviewable.
3. Your PR is a user-visible behavior change. What else must you add?
Reveal
A release-note entry under changelog/<version>/<release>/summary.md. User-focused — not internal implementation details.

Recap

  • Write a PR description with sections: What / Why / Test / Fixes.
