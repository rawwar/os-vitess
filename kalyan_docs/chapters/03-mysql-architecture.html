MySQL, layer by layer.

You don't need to be an InnoDB hacker to work on Vitess — but you need to know the names and shapes of the parts, because Vitess code references them constantly.

Why MySQL at all? Beginner

You picked Vitess to scale your database. So Vitess could have invented its own storage — but it didn't. It uses plain MySQL as the per-shard database, and acts as a coordinating layer above.

  • MySQL is well-understood, well-tooled, well-tested for 25+ years.
  • "It's just MySQL underneath" is Vitess's competitive advantage.
  • That means: every MySQL feature works inside one shard. But cross-shard behavior is Vitess's job.
Throughout this chapter
We're describing MySQL's server-layer behavior and InnoDB behavior. Both apply inside one shard. Cross-shard topics start in chapter 25.

MySQL is two databases in a trenchcoat

  • The server layer handles connections, parsing, planning.
  • The storage engine layer handles actual rows, indexes, transactions.
  • You'll hear "InnoDB" 100× more than the rest — it's the default, and the only one that gives transactions.

InnoDB: the engine you care about

  • Row-based, transactional. ACID, MVCC, crash-safe.
  • Clustered index on primary key. The PK is the table — leaf nodes contain the full row.
  • Secondary indexes point to PKs (not to row addresses).
  • B+ tree. 16 KB pages by default. Roughly log~100(N) levels for any lookup.
Why this matters for Vitess
Sharding keys are usually picked to be the PK (or a prefix). Vitess's vindexes encode "given this row's PK, which shard?" — chapter 20.

  • Internal nodes only hold keys; leaf nodes hold full rows.
  • Leaves are linked, so range scans are cheap.
  • Inserts can split pages — which is why bulk-insert order matters.

The four big logs you need to know

LogWho writesWhat it does
Redo logInnoDBReplay committed changes after a crash. Physical, circular.
Undo logInnoDBRoll back a txn; serve old row versions for MVCC reads.
BinlogServer layerLogical record of every write. Replication source. This is the one Vitess hooks into.
Slow logServer layerQuery > N seconds; debugging aid.
Binlog is the only one Vitess truly cares about
VReplication (chapter 21) is fundamentally "tail one tablet's binlog and apply rows to another tablet". Internalize this.

Transactions & MVCC, mentally

  • InnoDB never overwrites a row in place. Updates create a new version; old versions live in undo.
  • Each transaction gets a snapshot at start (REPEATABLE READ by default in MySQL).
  • Reads find the version visible to their snapshot; writers don't block readers.
  • That's why a slow read on a busy table makes the undo segment grow — and why it can hurt write performance.
Vitess implication
Long transactions through vtgate hold open connections in vttablet, which hold open MySQL transactions, which hold undo. Don't.

How Vitess talks about isolation

  • Vitess preserves MySQL isolation within a shard.
  • Across shards, default semantics are per-shard transactions — not globally atomic.
  • For cross-shard atomicity, Vitess supports MySQL XA / two-phase commit (2PC) — search the codebase for tx_mode, twopc, dtid.
  • 2PC has cost. Most apps don't enable it. Know it exists.

Common misconceptions

"The binlog is the same as the redo log"
No. The redo log is for crash recovery (InnoDB replays it on startup). The binlog is for replication and external consumers (other MySQLs, Vitess). Same idea — record every change — but different consumers, different formats, different writers.
"REPEATABLE READ means I can't see other people's changes"
Within your transaction, yes. But other people's COMMITs do hit the database; you just don't see them in your snapshot. The moment you start a new transaction, you'll see them.
"MyISAM is fine, ACID isn't required"
In 2026, just use InnoDB. MyISAM doesn't have transactions or row locks. Vitess assumes InnoDB.

Try it yourself Lab

15 min · any MySQL instance or Docker
  1. Open a MySQL prompt: mysql -uroot -p (or use the Docker container from chapter 3).
  2. Run these queries: 
    SHOW VARIABLES LIKE '%log_bin%';
SHOW VARIABLES LIKE '%isolation%';
SHOW ENGINE INNODB STATUS\G
What to notice
  • log_bin → ON in MySQL 8 by default. That's the binlog being written.
  • transaction_isolation → REPEATABLE-READ. That's the MVCC snapshot mode.
  • In INNODB STATUS, the BUFFER POOL AND MEMORY section shows how much page cache MySQL has and how full it is.
  • The TRANSACTIONS section lists every active transaction. If you ever debug "why is my Vitess shard slow?", this is the first place to look.

Checkpoint quiz Quiz

1. The "server layer" and "storage engine" — what's owned by which?
Reveal
Server layer: connection handling, auth, parsing, planning, the binlog. Storage engine (InnoDB): the actual rows on disk, the B+ tree, redo/undo logs, locks, MVCC.
2. Why does Vitess care more about the binlog than the redo log?
Reveal
The redo log is internal to one mysqld for crash recovery. The binlog is the external feed every other MySQL and every VReplication stream consumes. Vitess's data movement is built on tailing binlogs.
3. A user opens a transaction and walks away for 4 hours. Why does that hurt the whole MySQL?
Reveal
MVCC keeps old row versions in the undo log so the open transaction can still see its snapshot. Every concurrent write piles on more old versions. The undo log balloons; performance degrades for everyone.
4. Where in Vitess source would you start to learn how it consumes binlog events?
Reveal
go/mysql/binlog_event.go (event types and interface), go/mysql/binlog_event_mysql56.go (parser for MySQL 5.6+ events). Chapter 4 walks through this.
