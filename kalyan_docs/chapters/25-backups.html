Part V · Chapter 30

Backups.

The least glamorous, most critical subsystem. Vitess's design makes "restore a dead replica" a one-command operation.

Learning objectives

By the end of this chapter, you will
  • Define a backup = data files + binlog position.
  • Tell apart builtin and xtrabackup engines.
  • Restore a tablet from a backup in the local example.
  • Use vtbackup to take a backup without involving a production tablet.

The design idea

  • A backup = a snapshot of mysqld's data dir + a binlog position.
  • Restore = unpack the snapshot, replay binlogs from the position to "now".
  • Same path used for: disaster recovery, scaling out new replicas, vtbackup workflows.

Vitess decouples backup engines (how to capture) from backup storage (where to put bytes).

Two engines

EngineHow it worksTrade-off
builtinStop replica, copy files, restartSimpler; mysqld pause during backup
xtrabackupWraps Percona XtraBackupHot — no replica pause; needs external binary

Pick via flag --backup_engine_implementation.

  • go/vt/mysqlctl/builtinbackupengine.go
  • go/vt/mysqlctl/xtrabackupengine.go (if present in your tree)

Storage backends

  • file — local disk / NFS. filebackupstorage/
  • gcs — Google Cloud Storage. gcsbackupstorage/
  • s3 — implied via S3-compatible
  • azblob — Azure. azblobbackupstorage/
  • ceph — S3-compatible Ceph. cephbackupstorage/

All under go/vt/mysqlctl/backupstorage/.

The interface

// abridged from go/vt/mysqlctl/backupstorage/interface.go
type BackupStorage interface {
    ListBackups(ctx context.Context, dir string) ([]BackupHandle, error)
    StartBackup(ctx context.Context, dir, name string) (BackupHandle, error)
    RemoveBackup(ctx context.Context, dir, name string) error
    Close() error
}

type BackupHandle interface {
    Directory() string
    Name() string
    AddFile(ctx context.Context, filename string, size int64) (io.WriteCloser, error)
    ReadFile(ctx context.Context, filename string) (io.ReadCloser, error)
    EndBackup(ctx context.Context) error
    AbortBackup(ctx context.Context) error
}

It's just a streaming file API + atomic "this backup is done".

Taking a backup

vtctldclient Backup <tablet-alias>
# or
./401_backup.sh   # in the local example
  1. vtctld → tablet manager Backup RPC.
  2. Tablet sets itself NOT_SERVING (or uses RDONLY to avoid impact).
  3. Stops replication.
  4. Backup engine streams files into storage handle.
  5. Closes handle (atomic commit).
  6. Restarts replication; reverts state.

Restoring

  • vttablet on first start with empty data dir detects "I should be a tablet".
  • Calls RestoreFromBackup RPC on itself.
  • List backups → pick most recent compatible one.
  • Stream files into data dir.
  • Start mysqld.
  • Set up replication; wait for catch-up.
  • Mark tablet healthy.

End result: a fresh, in-sync replica from a single restart. This is the magic.

Point-in-time recovery (PITR)

  • Beyond plain restore: replay binlogs to a specific time.
  • RestoreFromBackup --restore-to-pos <gtid> or --restore-to-timestamp <ts>
  • Binlogs need to be archived separately (Vitess has options to back them up too).
  • Use case: "we deployed a bug at 14:32 that ran DELETE FROM users; restore to 14:31".

vtbackup: the standalone snapper

  • go/cmd/vtbackup/ — single-purpose binary.
  • Cron / K8s job:
    1. Spin up an isolated mysqld.
    2. Restore latest backup.
    3. Replicate to "now".
    4. Take a new backup.
    5. Exit.
  • No production tablet is impacted. Common pattern in operator-deployed clusters.

Compression & encryption

  • go/vt/mysqlctl/compression.go — pluggable: gzip, zstd, external command.
  • Compression often pays back massively for filesystem data (InnoDB ibd files).
  • Encryption at rest is the storage backend's responsibility (GCS / S3 server-side).
  • Encryption in transit handled by storage SDKs (HTTPS).

Manifest & metadata

  • Every backup includes a manifest JSON describing: backup time, position, files, hashes.
  • vtctldclient GetBackups commerce/0 lists them.
  • vttablet picks backups by name (timestamp) but also reads the manifest to confirm compatibility.

Try it yourself

30-min lab
  1. Run ./401_backup.sh; check $VTDATAROOT/backups/
  2. vtctldclient GetBackups commerce/0
  3. Stop a replica tablet, blow away its data dir, restart with vttablet ... --restore_from_backup.
  4. Watch it download, replay, come up healthy. (The local example's 403_restore_from_backup.sh does this dance.)

Part VI: how to actually contribute.

Checkpoint quiz

1. Restoring a fresh replica involves two steps. Name them.
Reveal
(1) Download the latest backup, unpack into the data dir. (2) Start mysqld and let it replicate from the current primary to catch up. The catchup step is just normal MySQL replication.
2. Why is vtbackup useful in Kubernetes deployments?
Reveal
A Kubernetes CronJob can run vtbackup periodically: it boots a one-off mysqld, restores latest backup, catches up, takes a new backup, exits. No production tablet is impacted.
