Part V · Chapter 26

VReplication.

The "tail a binlog and apply it somewhere else" engine that powers MoveTables, Reshard, and Materialize. Once you grok this, you grok 60% of Vitess's hard problems.

Learning objectives

By the end of this chapter, you will
  • Describe VReplication in one sentence: "tail one tablet's binlog, transform rows, apply on another."
  • Tell apart the copy phase and the running (catchup) phase.
  • Read the _vt.vreplication table on your local cluster.
  • Know that MoveTables, Reshard, Materialize, and Online DDL all share this engine.

One sentence definition

VReplication is a per-vttablet engine that follows another tablet's binlog, filters/transforms each row, and applies the result on its own mysqld.
  • Source = some tablet (often RDONLY) somewhere in the cluster.
  • Target = the local vttablet's mysqld.
  • Filter = a SQL expression that decides which rows match.
  • Bookkeeping in _vt.vreplication on the target.

Why one engine for so many things

  • MoveTables — copy a few tables from keyspace A to keyspace B.
  • Reshard — copy rows from old shards to new shards (matched by vindex).
  • Materialize — keep a derived table up to date via a SQL transform.
  • OnlineDDL via VReplication — copy rows from old table schema to new, applying schema changes.
  • Same primitive every time: follow a binlog, transform, apply.

The engine

  • go/vt/vttablet/tabletmanager/vreplication/engine.go — top-level Engine struct.
  • On startup, reads _vt.vreplication; for each row, spawns a controller goroutine.
  • Each controller manages one workflow on this target.

The controller

  • controller.go + controller_plan.go
  • Two phases:
    1. Copy phase — initial bulk copy of existing rows (vcopier.go)
    2. Catchup/Running phase — tail binlog and apply (vplayer.go)
  • Records position in _vt.vreplication.pos as a GTID set.

The copy phase

  • vcopier.go (and vcopier_atomic.go).
  • For each table in the workflow:
    1. SELECT rows from source in chunks, ordered by PK.
    2. INSERT them on target.
    3. Track "last PK copied" in _vt.copy_state.
  • While copying, the binlog event stream is buffered/replayed for the already-copied range so target stays consistent.

The running phase

  • vplayer.go
  • Opens a binlog stream on the source at the current position.
  • For each row event:
    1. Check filter (vschema/keyspace ID match).
    2. Transform values if needed.
    3. Build SQL: INSERT / UPDATE / DELETE on target.
    4. Apply, update position.
  • Throttler (go/vt/vttablet/tabletserver/throttle/) gates work so it doesn't drown the source/target.

The replicator plan

  • replicator_plan.go, table_plan_builder.go
  • Pre-computed: for each table, how to translate "source row → target row".
  • Handles: column renames, expression projections, filter WHERE, vindex match for resharding.
  • The plan is built once when the workflow starts; row events are cheap to apply.

VStream — the read side

  • The source tablet exposes a VStream RPC.
  • go/vt/vttablet/tabletserver/binlog_dump_engine.go — server side.
  • VStream events: BEGIN, FIELD, ROW, GTID, COMMIT.
  • Higher-level than raw binlog events — schema is already attached.

Other things consume VStream too: vtgate's VStream API, third-party CDC.

The state table: _vt.vreplication

SELECT id, workflow, state, pos, source FROM _vt.vreplication\G

One row per active VReplication stream on this tablet. state is one of:

  • Init — not yet started
  • Copying — initial copy in progress
  • Running — tailing binlog
  • Stopped — paused (often by error)
  • Lagging — falling behind
  • Error — see the message column

RPCs that drive workflows

  • Defined in rpc_vreplication.go:
    • CreateVReplicationWorkflow
    • ReadVReplicationWorkflow
    • UpdateVReplicationWorkflow — pause / resume / change source
    • DeleteVReplicationWorkflow
  • vtctldclient surfaces these via higher-level MoveTables create / show / cancel / complete.

VDiff: the verifier

  • Before cutting over, you want "are source and target equal?".
  • vdiff streams rows from both sides in PK order; compares.
  • Reports mismatches; never modifies.
  • Code: go/vt/vttablet/tabletmanager/vdiff/

Always vdiff before SwitchTraffic. It's the safety net.

Checkpoint quiz

1. What's the difference between the copy phase and the running phase?
Reveal
Copy: bulk select-from-source-and-insert-to-target, ordered by PK, in chunks. Running: tail the source's binlog and apply each event. After copy, the engine seamlessly switches to running mode at the captured GTID.
2. The same VReplication engine powers MoveTables, Reshard, Materialize, and Online DDL. What's different about each?
Reveal
The filter and target — MoveTables copies whole tables to another keyspace; Reshard filters by keyrange; Materialize applies a SQL transform; Online DDL writes to a shadow table with new schema. Engine doesn't care; it's just rows in, rows out.
3. Why is the throttler important here?
Reveal
VReplication runs in the background. If it overwhelms the source/target mysqlds, real production traffic suffers. The throttler tells VReplication to back off when replication lag rises on the primary's replicas.
