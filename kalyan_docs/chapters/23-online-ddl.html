Part V · Chapter 28

ALTER TABLE, without tears.

In big MySQL, an ALTER TABLE on a 1 TB table is an outage. Vitess offers online DDL strategies that copy rows behind the scenes.

Learning objectives

By the end of this chapter, you will
  • List the DDL strategies (direct, online/vitess, gh-ost).
  • Trace an online ALTER from submission to completion via _vt.schema_migrations.
  • Cancel a migration mid-run.

Why is ALTER hard?

  • MySQL 8's INSTANT and INPLACE work for some operations — but not all (most NOT NULL adds, fulltext, etc.).
  • For the rest, MySQL rewrites the entire table. Locks are minimal, but disk + IO load is huge.
  • On a hot table, replication lag explodes; failovers risk data loss.
  • Vitess provides strategies that wrap external tools or do it themselves.

The strategies

StrategyHow
directRun the ALTER as-is (no online magic)
online / vitessNative VReplication-based; default
gh-ostWrap gh-ost per shard
pt-osc(historical) Percona's pt-online-schema-change

Set via vtctldclient ApplySchema --ddl-strategy="online".

The "online" / "vitess" strategy

Mechanism: a one-off VReplication workflow per shard.

  1. Create a shadow table with the desired schema.
  2. VReplication copies + tails source → shadow.
  3. vdiff (optional).
  4. Cutover: swap table names (atomic-ish).
  5. Old table dropped (garbage collection delayed for safety).

You don't see any of this — you get a migration UUID and watch it progress.

Where it lives in code

  • go/vt/schema/ddl_strategy.go — parses the strategy spec.
  • go/vt/schema/online_ddl.go — the OnlineDDL state object.
  • go/vt/vttablet/onlineddl/executor.go — per-tablet executor; the state machine.
  • go/vt/vttablet/onlineddl/vrepl.go — the VReplication-based variant.
  • go/vt/vttablet/onlineddl/ghost.go — gh-ost wrapper.
  • go/vt/vttablet/onlineddl/schema.go — internal schema for tracking migrations.

State machine

  • Queued → Ready → Running → Complete / Failed / Cancelled
  • Each transition logged in _vt.schema_migrations.
  • Each shard runs its own migration concurrently; the workflow finishes when all shards complete.
SELECT migration_uuid, strategy, status, progress
FROM _vt.schema_migrations
ORDER BY id DESC LIMIT 10\G

Submitting a migration

vtctldclient ApplySchema \
    --ddl-strategy="vitess" \
    --sql "ALTER TABLE customer ADD COLUMN tier VARCHAR(16) NOT NULL DEFAULT 'standard'" \
    customer

Returns a list of migration UUIDs (one per shard). Then:

vtctldclient OnlineDDL show customer all
vtctldclient OnlineDDL show customer <uuid>
vtctldclient OnlineDDL cancel customer <uuid>
vtctldclient OnlineDDL retry customer <uuid>

Cutover & the "table swap"

  • The replacement table is created with a suffix like _vt_HOLD_....
  • At cutover, vttablet runs a RENAME TABLE original TO _old, shadow TO original atomically.
  • Old table is kept around (for the retain period) so you can roll back.
  • tablegc (go/vt/schema/tablegc.go) eventually drops it.

Throttling matters here too

  • VReplication-based ALTER backs off when the primary is busy (the throttler).
  • gh-ost has its own throttling knobs; Vitess passes through configuration.
  • Most production users tune the throttler before they tune the ALTER.

Postpone / launch / cleanup

  • Migrations can be submitted but postponed; you launch them during a maintenance window.
  • vtctldclient OnlineDDL launch <uuid> kicks off a postponed one.
  • cleanup drops the old shadow tables manually (instead of waiting for tablegc).

schemadiff: the planner side

  • go/vt/schemadiff/ — diff two schema definitions.
  • Used by Vitess to compute the diff when you provide a new full-table definition.
  • Also useful in code review: "tell me what ALTER this implies".

Try it yourself

30-min lab
  1. On your sharded customer keyspace: vtctldclient ApplySchema --ddl-strategy=vitess --sql "ALTER TABLE customer ADD COLUMN tier VARCHAR(16) DEFAULT 'std'" customer
  2. Watch progress: vtctldclient OnlineDDL show customer all
  3. Look on a target tablet: SELECT * FROM _vt.schema_migrations\G
  4. Try cancelling mid-run on a long ALTER: vtctldclient OnlineDDL cancel customer <uuid>

Checkpoint quiz

1. Why doesn't online DDL directly modify the original table?
Reveal
Big ALTERs rewrite the table — long-running, blocking, replication lag explodes. The shadow-table approach copies in the background, then renames atomically. Original table sees minimal disruption.
2. After cutover, what holds the "old" table?
Reveal
A renamed table like _vt_HOLD_.... It sticks around for a retention period (operator-configurable) so you can roll back. tablegc eventually drops it.
