Part V · Chapter 25

One keyspace, many shards.

Vitess's sharding is opinionated: range-based, key-space partitioning, with pluggable vindexes for mapping a column value to a key.

Learning objectives

By the end of this chapter, you will
  • Map a row to its shard given a vindex and shard layout.
  • Recognize the 10+ built-in vindex types and when each fits.
  • Read a vschema JSON and predict planner behavior.
  • Pick a sensible shard key and explain the trade-off.

From one table to two shards Mental model

You have a customer table. You decide to shard by customer_id. Two shards: -80 (covers half the key space) and 80- (the other half).

flowchart LR Insert["INSERT customer id=42, email=..."] --> Hash["hash(42) keyspace_id=0x2c..."] Hash --> Decide{"0x2c < 0x80?"} Decide -- yes --> ShardA["shard -80 primary + replicas"] Decide -- no --> ShardB[shard 80-]

The vindex maps the row's column value to an 8-byte keyspace ID. The keyspace ID picks a shard via the keyrange. That's the whole idea.

The vocabulary

TermMeaning
KeyspaceA logical database. Contains tables. Can be unsharded or sharded.
ShardOne slice of a sharded keyspace. Has its own primary + replicas.
KeyrangeThe slice's range: -80, 80-, -40, 40-80, etc.
Vindex"Vitess index" — a function: column value → keyspace ID (8-byte big-endian).
Keyspace IDThe 8-byte value used to place a row.
VSchemaThe config: which tables have which vindexes, in which keyspace.

How a row is placed

flowchart LR Row[INSERT customer
id=42, ...] --> Vindex[hash vindex
'id'] Vindex --> KID[keyspace id
8 bytes] KID --> Range[which range
contains it?] Range --> Shard[shard '40-80']
  1. For each primary vindex (your "shard key"), compute the keyspace ID from the row.
  2. Look up which shard's keyrange contains that ID.
  3. That's where the row goes.

The keyrange

  • Keyranges are hex strings, half-open: -80 = [00, 80), 80- = [80, FF].
  • Sharded keyspaces split the entire 8-byte space across shards (no gaps, no overlaps).
  • "0" (or -) means "the whole keyrange" — for unsharded.
All possible keyspace ids: 00 00 00 00 00 00 00 00  →  FF FF FF FF FF FF FF FF

2-shard split:  -80   covers 00..7F FF...
                80-   covers 80...FF FF...

4-shard split:  -40   40-80   80-c0   c0-

Built-in vindexes

  • hash — encrypted 3DES-based hash. Default for simple int PKs. go/vt/vtgate/vindexes/hash.go
  • binary — pass the raw bytes. For columns that are already uniform.
  • binary_md5 — md5 of bytes. For strings.
  • numeric — column value IS the keyspace ID.
  • numeric_static_map — file-driven lookup.
  • unicode_loose_md5 — string-aware (case-insensitive).
  • xxhash — fast non-crypto hash.
  • reverse_bits — for monotonically-increasing PKs (spread them around).
  • lookup, lookup_unique — a separate vindex table maps value → keyspace ID.
  • consistent_lookup — like lookup, but maintained transactionally.

The Vindex interface

// abridged from go/vt/vtgate/vindexes/vindex.go
type Vindex interface {
    String() string
    Cost() int
    IsUnique() bool
    NeedsVCursor() bool
}

type SingleColumn interface {
    Vindex
    Map(ctx context.Context, vcursor VCursor, ids []sqltypes.Value) ([]key.Destination, error)
    Verify(ctx context.Context, vcursor VCursor, ids []sqltypes.Value, ksids [][]byte) ([]bool, error)
}
  • Map answers "for this column value, which shard(s)?"
  • Verify answers "is this (value, ksid) pair correct?"
  • Cost() influences planner choice when multiple vindexes apply.

Primary vs secondary (lookup) vindexes

  • Primary — the vindex that defines a row's shard. Computed from a column on the row itself.
  • Secondary — additional vindexes on the table, used to route queries that filter on a different column.
  • Secondary vindexes are usually lookup-style: a separate table maps "secondary value" → primary value (or directly to keyspace ID).

Example: customer sharded by customer_id (primary hash); a lookup vindex on email lets WHERE email = 'x' still route to one shard.

        { "column": "customer_id", "name": "hash" }
      ]
    },
    "corder": {
      "column_vindexes": [
        { "column": "customer_id", "name": "hash" }
      ]
    }
  }
}

Reference tables & sequences

  • Reference tables — small lookup tables present on every shard. Cheap joins.
  • Configured in vschema: "type": "reference".
  • Sequences — Vitess's distributed auto-increment. A row in an unsharded sequence table; vtgate consumes it transactionally to allocate IDs.

Where the planner uses vindexes

  • SELECT with WHERE pk_col = N → planner calls vindex.Map(N) → one shard → Route(Equal).
  • SELECT with WHERE pk_col IN (1, 2, 3) → multi-shard route, deduped.
  • SELECT with no vindex predicate → Route(Scatter).
  • JOIN where both tables share the same vindex column → planner can co-locate the join on each shard.

Picking a sharding key

  • Most-frequent WHERE column on the table. (If you mostly query by user_id, shard by it.)
  • High cardinality (millions+ of distinct values).
  • Even distribution (avoid hot users).
  • Stable — changing the shard key value of a row means moving it across shards.
One-way decision
Changing your shard key after you have data means migrating every row. Pick carefully.

Predict the shard Practice

2-shard split: -80 and 80-, hash vindex
For each customer_id, which shard does the row land on?
  • customer_id = 1 → ?
  • customer_id = 42 → ?
  • customer_id = 1000 → ?
  • customer_id = 0 → ?
Reveal the answer
You can't know without computing the hash. That's the point: the hash vindex is intentionally not "id mod N shards" — that would put hot consecutive IDs on the same shard. The hash spreads them. To check yours, query: SELECT customer_id, keyspace_id() FROM customer WHERE customer_id IN (1, 42, 1000, 0); after running 301_customer_sharded.sh.

Checkpoint quiz

1. Why is changing the shard key after data exists a one-way decision?
Reveal
Changing the shard key value of a row would move it to a different shard. With billions of rows, that's a multi-day migration with downtime risk. Pick once, very carefully.
2. SELECT * FROM customer WHERE email = 'a@x.com'. Without a lookup vindex on email, what does vtgate do?
Reveal
Scatter — send the query to every shard. With a lookup vindex on email, vtgate first queries the lookup table to find the keyspace ID, then routes to one shard.
3. Why is a reference table kept on every shard?
Reveal
So sharded queries can JOIN against it without crossing shards. Common for tiny lookup tables (country codes, product categories) where the cost of duplication is trivial.
