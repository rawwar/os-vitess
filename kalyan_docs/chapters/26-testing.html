Part VI · Chapter 31

Testing.

Vitess has three test tiers. Knowing which one to write — and which one to run before pushing — saves a lot of time.

Learning objectives

By the end of this chapter, you will
  • Run unit tests for a single package locally.
  • Run planner tests and read the diff when something changes.
  • List e2e suites and pick the one relevant to your change.
  • Use gofumpt, goimports, and make lint as a pre-commit checklist.

The three tiers

TierWhereSpeedWhat it catches
UnitCo-located *_test.goSecondsLogic regressions, edge cases
Plango/vt/vtgate/planbuilder/testdata/SecondsPlanner regressions
End-to-endgo/test/endtoend/MinutesWhole-cluster behavior

Unit tests

# Run tests in a single package
go test ./go/vt/sqlparser/...

# Verbose
go test -v ./go/vt/topo/...

# Specific test
go test -run TestParse ./go/vt/sqlparser/

# With race detector
go test -race ./go/pools/...
  • Stick to testify/assert & testify/require per CLAUDE.md.
  • t.Context() > context.Background().
  • t.Cleanup for teardown.

Planner tests: a special case

  • Located in go/vt/vtgate/planbuilder/testdata/
  • JSON files: SQL in, expected plan out.
  • Test runner: plan_test.go in the same package.
# Update plans (after a planner change)
go test -run TestPlan ./go/vt/vtgate/planbuilder/ -update-plans
# Inspect the diff in testdata before committing!

This is how every planner change gets reviewed — diff the testdata, see what behavior moved.

End-to-end tests

  • go/test/endtoend/ — each subdir is a feature area.
  • Tests spin up a real (small) Vitess cluster, run SQL through it, check results.
  • Slow but high-confidence. CI runs these in matrix across MySQL flavors.
  • Driver script: test.go at repo root.

Running e2e tests

# List the test suites
./test.go list

# Run a specific suite locally
./test.go -keep -- vtgate

# Just compile, don't run (smoke test)
go test -tags integration ./go/test/endtoend/vtgate/... -run xxx
Slow but worth it
Don't run all e2e tests on every push — pick the suite related to your change. CI runs the full matrix; trust CI for that.

Mocks, fakes, helpers

  • memorytopo — in-memory topo for tests (go/vt/topo/memorytopo/)
  • faketopo — partial topo for unit tests
  • fakerpcvtgateconn — fake vtgate gRPC for tablet tests
  • sandboxconn — fake tabletconn (vtgate's view of a vttablet)
  • fakemysqldaemon — pretends to be mysqld for mysqlctl tests

Search for them when you need to stub a layer instead of standing up a real one.

When in doubt: what test do I write?

  • Fixing a planner bug: add a row to the relevant testdata/*.json; let plan tests fail; fix planner; re-update plans.
  • Adding a vttablet RPC: unit test in rpc_*_test.go; ensure mock client works; add e2e if it crosses tablets.
  • Adding a sysvar: unit test in sysvars/; planner test that confirms the SET is intercepted correctly.
  • Touching reparent: unit test + e2e under endtoend/reparent/. ERS is too important to test only by hand.

Flaky tests & what to do about them

  • Vitess CI has its share of flakes — GitHub runners are resource-starved.
  • CLAUDE.md rule: timeouts ≥ 30s; assert.Eventually not time.Sleep.
  • If a test fails sporadically: look for time-based assumptions first.
  • Use t.Logf generously when investigating — output lands in CI logs.

Coverage

go test -coverprofile=cover.out ./go/vt/vtgate/...
go tool cover -html=cover.out

Not enforced as a number, but PRs are expected to add tests for new behavior. "I tested it manually" isn't enough.

Linters & formatters

make lint                 # runs golangci-lint
gofumpt -w <changed-files>
goimports -local "vitess.io/vitess" -w <changed-files>

Run these before pushing. CI will run them again; failing CI for formatting is embarrassing.

Try it yourself Lab · 20 min

Run real Vitess tests on your machine
  1. Run the parser's unit tests: 
    go test ./go/vt/sqlparser/...
    Should finish in ~2 seconds.
  2. Run the planner tests: 
    go test -run TestPlan ./go/vt/vtgate/planbuilder/ -count 1
  3. List e2e suites: 
    ./test.go list | head -30
  4. Open a random testdata/*_cases.json; pick one entry; read it:
    ls go/vt/vtgate/planbuilder/testdata/ | head
less go/vt/vtgate/planbuilder/testdata/select_cases.json
What to notice
  • Plan tests are JSON pairs of SQL → expected plan. Easy to add new cases.
  • Unit tests are fast — sub-second per package. Run them on every save.
  • e2e tests are slow but high-confidence. Use selectively.

Checkpoint quiz

1. You change the planner. Which tier breaks first?
Reveal
Plan tests. Run go test ./go/vt/vtgate/planbuilder/. The output shows expected vs. actual JSON diff — easy to read.
2. A unit test passes locally but flakes in CI. What's the most likely cause per CLAUDE.md?
Reveal
A time-based assumption: time.Sleep(100*time.Millisecond) or a sub-second timeout. CI runners are starved; use assert.Eventually with a 30s timeout instead.
3. Three commands you should run before every git push?
Reveal
gofumpt -w, goimports -local "vitess.io/vitess" -w, and the targeted unit tests for your package. Lint and full e2e can wait for CI.

Recap

You should now be able to
  • Run unit tests for any package and read failures.
  • Run and update planner tests.
  • Find the right e2e suite for a given change.
  • Avoid the top-3 CI fail reasons (format, lint, sleep-based flakes).
