Where everything lives.

An annotated tour of the top-level directories. Bookmark this chapter; you'll come back.

Learning objectives

By the end of this chapter, you will
  • Recognize go/, proto/, examples/, test/ at the top level.
  • Tell which directories under go/vt/ matter for which subsystem.
  • Know the rule: never edit anything labeled "Code generated … DO NOT EDIT".
  • Locate the entrypoint of any Vitess binary in under 30 seconds.

go/vt/ — the implementation

  • vtgate/ — planner, executor, plan tests, vindexes
  • vttablet/ — tabletserver (query path), tabletmanager (control), vreplication, onlineddl
  • vtctld/, vtctl/, wrangler/ — admin / workflow code
  • vtorc/ — failover daemon
  • topo/ — topology service abstraction + implementations
  • sqlparser/ — SQL parsing, AST, normalizer, formatter
  • mysqlctl/ — managing mysqld + backups
  • schema/, schemadiff/ — schema tracking and diffing
  • binlog/ — binlog consumption helpers
  • vterrors/ — error wrapping with gRPC codes
  • proto/ — generated Go code from proto/

go/ support libraries (not vt-specific)

  • go/mysql/ — wire protocol, binlog events, charsets
  • go/pools/ — generic pool primitives
  • go/sqltypes/ — the canonical row/value type. You'll see sqltypes.Value everywhere.
  • go/sqlescape/ — SQL identifier/literal escaping
  • go/cache/ — TheineW cache, used for prepared statement caching, etc.
  • go/stats/ — Vitess's own metrics library (predates Prometheus)
  • go/trace/ — distributed tracing helpers (OpenTelemetry-backed)
  • go/event/ — pub/sub helpers for cluster events

Inside go/vt/vtgate/

  • executor.go — top-level "given SQL, give me a result"
  • plan_execute.go — runs a plan against the cluster
  • planbuilder/ — SQL → plan (huge, recursive)
  • engine/ — plan primitives: Route, Join, Limit, Aggregate
  • vindexes/ — sharding functions (hash, lookup, consistent_lookup, …)
  • evalengine/ — pure-Go expression evaluator (constants, simple math)
  • buffer/ — buffers writes during reparents
  • plugin_mysql_server.go — the MySQL Handler for vtgate

Inside go/vt/vttablet/

  • tabletserver/ — the query path. QueryService interface, query rewriting, conn pools, transaction engine.
  • tabletmanager/ — the control path. RPCs from vtctld; ChangeType, Reparent, Backup.
  • tabletmanager/vreplication/ — VReplication engine
  • onlineddl/ — online DDL state machine
  • tabletconn/, grpctabletconn/ — vtgate → vttablet client
  • tmclient/, grpctmclient/ — vtctld → vttablet client

proto/ — the source of truth for RPCs

  • Every gRPC service in Vitess has a .proto here.
  • topodata.proto, vtgate.proto, query.proto, tabletmanagerdata.proto, etc.
  • Generated Go lives in go/vt/proto/<name>/ with a "DO NOT EDIT" header.
  • To change wire schemas: edit .proto + run make proto.
House rule
Never edit anything under go/vt/proto/ directly. Run make proto. (See CLAUDE.md, "Protobufs".)

go/test/endtoend/

  • Real Vitess clusters spun up by tests; SQL run against them.
  • Hundreds of subdirs, organized by feature: vreplication/, onlineddl/, sharding/, vtgate/, …
  • Slow — these are the "did we break anything serious?" gate.

We learn how to run them in chapter 26. They live behind ./test.go.

Top-level files worth opening once

  • CLAUDE.md — the style guide. Already cited many times in this tutorial.
  • CONTRIBUTING.md — short; mostly points at vitess.io/contributing.
  • Makefile — discoverable: make help, make build, make proto, make codegen.
  • bootstrap.sh + dev.env — set up the Go toolchain, MySQL flavor, etc.
  • test.go — runs end-to-end suites.

Checkpoint quiz

1. You want to change a gRPC schema. Which file do you edit, and what command do you run after?
Reveal
Edit the .proto file under proto/. Run make proto to regenerate Go code under go/vt/proto/. Never edit go/vt/proto/ by hand.
2. Where would you start reading to understand vttablet's query path?
Reveal
go/vt/vttablet/tabletserver/tabletserver.go, then query_engine.go and tx_engine.go next to it.
3. Where do end-to-end tests live, and why are they slow?
Reveal
go/test/endtoend/. Each test boots a small real cluster (mysqld + vtctld + vtgate + vttablets) and runs SQL through it. Reality > speed for these.

Recap

You should now be able to
  • Find any subsystem's code from its name (vtgate, vttablet, sqlparser, mysqlctl, …).
  • Recognize generated files by their first line.
  • Know where to ignore (Java, vtadmin web) until later.
