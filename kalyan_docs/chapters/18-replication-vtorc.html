Part IV · Chapter 23

The autopilot.

VTOrc detects bad replication topologies and fixes them. It's the part of Vitess that wakes you up less.

Learning objectives

By the end of this chapter, you will
  • Describe vtorc's loop: probe → analyze → act.
  • Name 3+ anomaly types vtorc reacts to.
  • Connect vtorc to the tabletmanager RPCs from the previous chapter.
  • Find vtorc's HTTP UI on your local cluster.

What VTOrc does

  • Probes every tablet's MySQL frequently.
  • Builds an in-memory model of the replication topology.
  • Detects anomalies: dead primary, broken replication, demoted primary, replication lag.
  • Decides on a recovery (PRS or ERS), then calls vtctld to do it.

It's a Vitess-flavored fork of openark/orchestrator, an older MySQL-only tool.

VTOrc layout

  • go/cmd/vtorc/ — binary entrypoint
  • go/vt/vtorc/inst/ — "instance" model (tablet + MySQL state)
  • go/vt/vtorc/db/ — SQLite-backed state cache
  • go/vt/vtorc/logic/ — the heart: discovery, analysis, recovery
  • go/vt/vtorc/process/ — leadership election (only one VTOrc acts at a time)
  • go/vt/vtorc/server/ — HTTP/RPC for the UI & API

Discovery loop

flowchart LR Topo[(topo)] --> Discover[every N seconds
discover tablets] Discover --> Probe[probe each tablet's mysqld] Probe --> Store[update SQLite cache] Store --> Analyze[analyze anomalies] Analyze --> Decide{recovery needed?} Decide -- yes --> Act[call vtctld] Decide -- no --> Discover

Defaults: ~5s discovery interval, ~10s probe. Tunable.

The anomaly catalog

Search for AnalysisCode in go/vt/vtorc/inst/analysis.go. A few:

  • DeadPrimary — primary can't be probed; replicas confirm they can't reach it either
  • DeadPrimaryAndReplicas — even worse
  • ReplicaIsWritable — read_only flipped off; suspicious
  • NotConnectedToPrimary — replica thinks it has no source
  • ReplicationStopped — IO/SQL threads stopped

For each, there's a recovery action.

Recovery decisions

  • go/vt/vtorc/logic/topology_recovery.go — the dispatcher.
  • For DeadPrimary: call ERS on the shard.
  • For ReplicaIsWritable: set read_only = ON.
  • For ReplicationStopped: try START REPLICA; escalate if it fails.
  • Cooldowns prevent thrash — VTOrc won't retry the same shard for X seconds after a recovery.

ERS, in code

  • VTOrc doesn't reimplement reparent — it calls vtctld.
  • vtctld implementation: go/vt/vtctl/reparentutil/emergency_reparenter.go
  • Skeleton:
    1. Lock the shard in topo.
    2. Stop replication on all reachable replicas; collect positions.
    3. Pick the most-advanced replica (deterministic tie-break).
    4. Promote it (set read_only=OFF, update topo).
    5. Re-parent the rest to it.
    6. Update the shard record's primary alias.
    7. Unlock.

Why "most-advanced replica" matters

  • With async replication, replicas lag the primary.
  • When the primary dies suddenly, each replica is at a different GTID.
  • Promoting a less-advanced replica = data loss (transactions on the dead primary are gone).
  • Semi-sync helps: at least one replica had the data when the primary acked the client.
Read this in code
go/vt/vtctl/reparentutil/util.go · the helper that chooses the candidate. Pay attention to the explicit tie-breaks.

Leadership: only one VTOrc decides

  • You typically run 3 VTOrcs per cluster for HA.
  • They elect a leader via topo (etcd lease, ZK ephemeral, …).
  • Only the leader probes & acts; followers stand by.
  • If the leader dies, a follower takes over within seconds.

See go/vt/vtorc/process/election.go.

Vitess vs. classical Orchestrator

  • Classical Orchestrator: works on raw MySQLs, no notion of "Vitess shard".
  • VTOrc: aware of Vitess tablet types & topo; calls vtctld, not direct MySQL DDL.
  • Removes the "split brain with another reparent tool" risk.
  • If you ever inherit a Vitess + Orchestrator hybrid: migrate to VTOrc.

The HTTP UI

  • go/vt/vtorc/server/ serves a small HTML UI at /web/.
  • Shows current topology, recent recoveries, anomalies.
  • Great for "why did failover happen at 3am" forensics.

Try it yourself

20-min walk
  1. Find VTOrc's port in your local cluster: cat $VTDATAROOT/tmp/vtorc.INFO | head -20
  2. Open http://localhost:<port>/api/cluster-info — JSON of cluster state.
  3. Read go/vt/vtorc/logic/topology_recovery.go top: see the recovery dispatch table.
  4. Simulate a failure: kill the primary tablet (kill <pid>); watch VTOrc fail over within ~30s.

Lab: simulate a failover Lab · 15 min

Kill a primary, watch vtorc recover
  1. With local cluster up, find the primary tablet: 
    vtctldclient GetTablets --keyspace commerce | grep primary
  2. Tail vtorc's log: 
    tail -f $VTDATAROOT/tmp/vtorc.INFO
  3. In another terminal, find the primary's PID and kill it: 
    ps aux | grep vttablet_0000000100 | grep -v grep
kill <pid>
  4. Within ~30 seconds, vtorc detects the dead primary, runs ERS, promotes a replica.
  5. Re-check tablets: 
    vtctldclient GetTablets --keyspace commerce | grep primary
    Now a different tablet is primary.
What to notice in vtorc's log
Look for lines mentioning DeadPrimary → RecoverDeadPrimary → PromoteReplica. That's the analysis-decision-action chain.

Checkpoint quiz

1. How many vtorcs run in production, and why?
Reveal
Usually 3 for HA. Only one is leader (via topo leadership election); the others stand by. If the leader dies, a follower takes over within seconds — same model as etcd or Kubernetes controllers.
2. After a recovery, vtorc enters a cooldown for the affected shard. Why?
Reveal
Prevents thrash. If the just-promoted primary briefly looks unhealthy (network blip), a cooldown stops vtorc from immediately re-failing-over. Stability > speed of reaction.
