Part 0 · Chapter 5

Move through the repo, safely.

Vitess is a big repo with ~5000 Go files. Here's the small set of terminal moves you'll use every day — and the safety rules so you never accidentally destroy your local copy.

What this chapter gives you

By the end of this chapter, you will
  • Navigate any repo with cd, ls, and pwd without thinking.
  • Search code with rg (ripgrep) — orders of magnitude faster than grep.
  • Read files with less / bat instead of needing your editor for every peek.
  • Inspect git history (git log, git blame, git diff) without modifying anything.
  • Know exactly which commands are safe and which can destroy uncommitted work.

The goal of this chapter is fluency, not knowledge. You'll be running these commands hundreds of times across the rest of the course; the faster they become muscle memory, the more you'll enjoy the rest.

The safety hierarchy

Three buckets of commands. Memorize the third one — those are the only ones that can destroy work.

CategoryCommands
Always safels, cat, less, head, tail, wc, rg, find, git status, git log, git diff, git blame
Safe-ish — read the promptgit checkout <file> (reverts uncommitted edits), git stash, rm, mv
Can destroy work — be carefulgit reset --hard, git clean -fd, git push --force, rm -rf
Rule of thumb
If a command starts with git push --force, rm -rf, or git reset --hard, stop and re-read the path. CLAUDE.md (the repo's contributor guide) explicitly forbids force-push to PR branches once review has started, for exactly this reason — they're irreversible on a shared branch.

Navigation: the four moves

You need four commands, total, to move around a repo:

# Where am I?
pwd

# What's here?
ls
ls -la                 # include hidden files (.git, .github)

# Walk somewhere
cd go/vt/vtgate

# Go back up
cd ..
cd -                   # back to the previous directory you were in

That's enough to navigate any project. The Vitess repo root has these top-level directories you'll visit constantly:

  • go/ — all Go source. About 95% of the code lives here.
  • proto/ — protobuf definitions (gRPC schemas).
  • examples/local/ — the canonical local cluster demo.
  • kalyan_docs/ — this tutorial.
  • CLAUDE.md — the contributor style guide. You'll re-read it more times than you expect.

Pro tip: configure your shell to enable tab completion. After typing cd go/vt/vtg, pressing Tab should complete to cd go/vt/vtgate/. If it doesn't, your shell's autocomplete needs setup — worth fixing for the rest of this course.

Searching with rg (ripgrep)

The single most-used command in the rest of this course will be rg — ripgrep, a faster, smarter grep. It respects .gitignore, so it won't pollute your search with build artifacts or vendored dependencies.

# Find a string anywhere in the repo
rg "ScatterConn"

# Just in .go files
rg --type go "ScatterConn"

# Just file names that match (no content search)
rg --files | rg vtgate

# Whole-word match, case-insensitive
rg -wi "executor"

# Show 3 lines of context around each match
rg -C 3 "ScatterConn"

# Search in a specific subdir
rg "Replicate" go/vt/vttablet/

# Count matches per file
rg --count "TODO"
Why not grep?
grep works but is 10–100× slower on large repos. Worse, it'll happily search node_modules and binary files unless you tell it not to. rg is what every Vitess maintainer uses; if you ever pair with one, this is the tool you'll see them reach for first.

If rg isn't installed: brew install ripgrep on macOS, apt install ripgrep on most Linux distros.

Reading files without opening an editor

You don't need to launch your editor for every quick peek at a file. Three commands cover most needs:

# Open a file in a pager (q to quit, /pattern to search, n for next)
less go/vt/vtgate/executor.go

# First 100 lines
head -100 go/vt/vtgate/executor.go

# Last 100 lines (useful for logs)
tail -100 $VTDATAROOT/tmp/vtgate.INFO

# Live-tail a log as new lines arrive
tail -f $VTDATAROOT/tmp/vtgate.INFO

Inside less: q quits, /foo searches forward for "foo", n jumps to the next match, g goes to the top, G goes to the bottom. h shows help. That's the whole user interface.

If you've got bat installed (brew install bat), it's cat with syntax highlighting and line numbers — wonderful for reading code:

bat go/vt/vtgate/executor.go

And of course your editor (VS Code, Cursor, etc.) is also fine — sometimes better than a terminal pager. Use whichever is fastest in the moment.

Git: read-only commands

Git is huge, but you only need a handful of read-only commands to learn the codebase's history.

git status              # what's changed in my checkout right now?
git log --oneline -10   # last 10 commits, one line each
git log --oneline --author='Sugu' -10
git log -p path/to/file # commits PLUS their diffs for one file
git diff                # what I've changed but not committed
git diff main           # difference between my branch and main
git branch --show-current

None of these commands change anything. They're pure reading. Use them freely as you explore the codebase — they're often the fastest way to answer "why does this code look like this?"

One you'll especially come to love: git blame.

git blame to read history

git blame shows, for each line in a file, the last commit that touched it. It's how you find out who wrote what — and more importantly, when and why.

git blame -L 100,150 go/vt/vtgate/executor.go

For each of lines 100–150, you'll see the commit hash, the author, the date, and the line content. Copy the commit hash and you can dig deeper:

git show 1a2b3c4d         # full commit: message, author, all changes
git log 1a2b3c4d -1       # just the message
How to find the "why"
Got a confusing line? git blame it, get the commit hash, git show it. The commit message almost always answers your question — that's what messages are for. If the message is weak, look at the PR (search GitHub for the commit hash).

Git: commands that change things

These do modify state. Read carefully before running each one.

  • git checkout -b my-branch — create and switch to a new branch. Safe.
  • git add <file> — stage a file for commit. Safe (no commit yet).
  • git commit --signoff -m "msg" — record a commit. Easy to undo with git reset HEAD~1 if you change your mind.
  • git push origin <branch> — upload your branch to your fork. Recoverable.
  • git checkout main — switch branches. Safe as long as you don't have uncommitted conflicting changes.
  • git stash — set aside uncommitted changes temporarily. Reversible with git stash pop.
Avoid these in this tutorial
git reset --hard, git push --force, git clean -fd, and rm -rf .git. Each can lose uncommitted work permanently. We don't need any of them. If you accidentally make a mess, git stash + git status is almost always enough to recover.

Environment variables you'll meet

Three environment variables drive Vitess's local development setup. They're set when you source dev.env (chapter 14 walks through this). For now, just know they exist:

  • $VTROOT — root of your Vitess source tree (usually the repo directory).
  • $VTDATAROOT — where the local example stores everything stateful: etcd state, per-tablet mysqld data dirs, logs.
  • $PATH — must include Vitess bin/ so you can run vtgate, vttablet, etc. without absolute paths.

You can inspect them at any time:

echo $VTROOT
echo $VTDATAROOT
echo $PATH | tr ':' '\n'    # print PATH one entry per line

If $VTDATAROOT is unset, that's normal until you source dev.env. The local-cluster scripts in chapter 14 will set it for you.

Lab: explore the repo without changing it

15 min · read-only
  1. From the repo root: 
    pwd && ls
  2. How many Go files are in the repo? 
    rg --files --type go | wc -l
  3. How many files mention ScatterConn? 
    rg --files-with-matches "ScatterConn" --type go | wc -l
  4. Who last touched go/vt/vtgate/executor.go line 1? 
    git blame -L 1,1 go/vt/vtgate/executor.go
  5. Read the contributor style guide: 
    less CLAUDE.md
# press q to quit
What to notice
  • About 5000 Go files. Vitess is large, but each file is small — usually under 1000 lines.
  • ScatterConn shows up in 30+ files, which tells you it's a foundational type.
  • The first line of every Vitess Go file is the Apache 2.0 license header. Git blame's first line shows whichever commit added that license header originally.
  • CLAUDE.md is the cheat-sheet you'll re-read whenever you forget a convention. Skim it now; come back later.

Troubleshooting cheat-sheet

You will hit each of these at least once. Here's what to do:

ProblemWhat to try
command not found: rgmacOS: brew install ripgrep. Linux: apt install ripgrep or yum install ripgrep.
"permission denied" running ./script.shchmod +x ./script.sh then re-run.
"port already in use" when running examplesOld process still alive. lsof -i :PORT to find the PID, then kill <pid>.
Accidentally edited a file you shouldn't havegit diff <file> to see what changed, then git checkout -- <file> to revert.
Lost track of many open terminal tabsUse tmux or your terminal's split-window feature. Two splits — one for editor commands, one for log tailing — usually does the job.
"too many open files" running the local clusterulimit -n 10000 in your shell.

Checkpoint quiz

1. Which command searches a string across the whole repo, automatically skipping .gitignore'd files?
Reveal
rg "string". By default ripgrep respects .gitignore. Use rg -u "string" if you want to ignore that and search everything.
2. You accidentally edited CLAUDE.md. How do you discard the change without committing?
Reveal
git checkout -- CLAUDE.md (or in newer git: git restore CLAUDE.md). It reverts the file to the last commit. Confirm with git status — it should no longer be listed as modified.
3. What's the difference between git log and git blame?
Reveal
git log walks commits in time order. git blame walks per line: for each line in a file, which commit last touched it. Different views of the same history.
4. You see a confusing line in go/vt/vtgate/executor.go. What's the fastest way to find out why it's like that?
Reveal
git blame -L <line>,<line> go/vt/vtgate/executor.go to get the commit hash, then git show <hash> to read the full message and diff. If the message is thin, search GitHub for the hash to find the PR.
