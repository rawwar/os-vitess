The control surface.

When vtctld says "reparent" or "backup", it's calling these RPCs. The list is a great map of what a vttablet can do.

Learning objectives

By the end of this chapter, you will
  • List the major RPC files (rpc_replication.go, rpc_backup.go, ...).
  • Tell apart PRS (planned) and ERS (emergency) reparent.
  • Know why ERS code is "do not casually touch" territory.

The reparent primitives

In rpc_replication.go:

  • DemotePrimary — stop accepting writes, return current position
  • UndoDemotePrimary — go back to PRIMARY (used if reparent aborts mid-way)
  • PromoteReplica — promote this REPLICA to PRIMARY
  • SetReplicationSource — point this tablet at a new source
  • StopReplicationAndGetStatus — for ERS, find each replica's position
  • WaitForPosition — wait until a tablet reaches a GTID

These are the building blocks vtctld composes into PlannedReparentShard and EmergencyReparentShard.

PlannedReparentShard (PRS)

  • You know the current primary is alive. You're just moving it.
  • Algorithm (rough):
    1. DemotePrimary on old primary → returns last position
    2. WaitForPosition on the new primary candidate
    3. PromoteReplica on the candidate
    4. SetReplicationSource on all the others → point at new primary
  • Reliable. Use this for routine ops.

EmergencyReparentShard (ERS)

  • Primary is dead or unreachable.
  • Must reason from replicas only.
  • Find the most-advanced replica via StopReplicationAndGetStatus.
  • Promote it; reset everyone else to follow.
CLAUDE.md house rule
"ERS must prioritize certainty that we picked the most-advanced candidate. Changes should prioritize reducing points of failure — avoid new RPCs or work that may delay or make ERS more brittle." Read that twice before touching these files.

tabletmanager state & init

  • tm_init.go — bootstrap a tablet: read topo, decide tablet type, register with healthcheck.
  • tm_state.go — in-memory state for the tablet (type, replication state, etc.).
  • shard_sync.go — keeps the tablet's view of its shard in sync with topo (e.g. learns of a new primary via watch).
  • shard_watcher.go — watches topo for shard-level events.

VDiff

  • go/vt/vttablet/tabletmanager/vdiff/ — full sub-package.
  • Compares rows on the VReplication source vs. target.
  • Used to verify a MoveTables or Reshard before cutting over.
  • RPC entry points in rpc_vdiff.go.
Pattern to internalize
Any time Vitess copies data (MoveTables, Reshard, Materialize), there's a matching verify step. VDiff is that verify.

Backups, from the tablet's view

  • rpc_backup.go — Backup RPC, RestoreFromBackup.
  • Delegates to go/vt/mysqlctl/ for the actual file work.
  • While a backup runs, vttablet sets itself NOT_SERVING.
  • RDONLY tablets are usually used as backup sources to avoid replica-traffic impact.

Locking tables

  • rpc_lock_tables.go — LockTables, UnlockTables.
  • Used by VReplication during the cutover phase to freeze writes briefly.
  • Backed by MySQL's LOCK TABLES.

Try it yourself

15-min walk
  1. vtctldclient PingTablet zone1-100 — find a tablet alias from GetTablets.
  2. That hits Ping in rpc_actions.go. Open it; one-liner.
  3. Read DemotePrimary in rpc_replication.go — appreciate how careful it is.
  4. Find PromoteReplica. Note where it logs and on what context-cancel rules.

Checkpoint quiz

1. When does vtctld call DemotePrimary?
Reveal
During PlannedReparentShard (PRS), when the old primary is alive but being replaced. ERS skips DemotePrimary because the primary is dead.
2. Why is "most-advanced replica" a fragile concept across async replicas?
Reveal
Without semi-sync, the primary may have committed transactions no replica saw. "Most-advanced" picks the best of bad options. Semi-sync guarantees at least one replica has the data the primary acked.
3. Why does the CLAUDE.md house rule warn against touching ERS code lightly?
Reveal
ERS runs when something is already broken. New RPCs or extra hops add new failure modes precisely when reliability matters most. "Reduce points of failure" trumps clever optimizations here.
